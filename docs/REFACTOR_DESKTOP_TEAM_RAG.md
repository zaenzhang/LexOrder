# LexOrder 重构评估：个人安装版、团队自部署与内置 RAG

更新与资料核验日期：2026-11-16。

**状态：产品目标已确认，工程方案为推荐路线，具体选型与性能尚待原型验证。本轮交付为文档，不代表桌面安装包、Rust 后端、SQLite 适配或 RAG 已实现。**

评估的当前代码基线为 LexOrder `3a800b8b1b6d26110afad34bfdded1a852341fa9`；现有应用仍是 Next.js / React / TypeScript / Prisma / PostgreSQL。业务增量见 [WORKBENCH_PLAN.md](WORKBENCH_PLAN.md)，执行状态见 [PROJECT_HANDOFF.md](PROJECT_HANDOFF.md)。本文更新交付形态、RAG 定位与重构方向；历史发布、测试和工期记录不作为新架构的完成证明。

## 1. 已确认的产品目标

| 决策 | 要求 | 对实现的影响 |
| --- | --- | --- |
| 个人独立使用 | 提供可安装应用，用户不必手工维护一套服务器 | 文件、索引、任务、必要运行组件由应用管理 |
| 团队协作 | 团队可以自行部署，成员通过浏览器或桌面客户端使用 | 一套团队服务集中鉴权和处理共享数据，不要求每人部署后端 |
| RAG 必备 | 个人版与团队版都提供基于材料的检索、问答和来源引用 | RAG 进入共同能力范围；具体检索产品可以替换 |
| 尽可能保留功能 | 保留客户、收案、案件、期限、财务、审批、材料、文书、归档及其业务规则 | 用行为与数据一致性逐项验收，不能以更换语言或数据库为由静默删减 |
| SQLite 为选项 | 不将全系统替换为 SQLite 作为前提 | 业务数据库与 RAG 索引分别评估；保留 PostgreSQL 路线 |
| 重构优先 | 重点评估 Rust 与桌面交付，吸收相关项目的核心逻辑 | 重新划分业务边界，迁移有价值的模块；不预先承诺全面重写的收益 |
| 参考方式 | 直接研究核心规则、处理流程和交互，结合 LexOrder 独立实现 | 从行为规格、输入输出和验收场景形成设计；研究范围不按项目协议类型排除 |

“个人独立”包括无需团队服务器即可维护本人的工作区；“完全离线”还要求所用 OCR、嵌入、重排及生成模型均能本地运行。两种要求分别验收。

团队版延续“一家团队一套实例”的部署方式。跨设备自动同步、离线共同编辑、共享 SaaS 多租户均不是由上述要求自动推出的承诺。

## 2. 推荐的交付方式

### 2.1 同一套业务与 RAG 核心，两种运行入口

| 方面 | 个人安装版 | 团队自部署版 |
| --- | --- | --- |
| 用户入口 | 安装并创建个人工作区 | 管理员部署，成员登录团队地址 |
| 业务执行 | 本机应用核心 | 团队服务端 |
| 业务存储 | SQLite 与应用托管 PostgreSQL 继续对比，以功能兼容结果定默认值 | PostgreSQL 为优先保留方案 |
| 材料与 RAG | 本机文件、解析任务及嵌入式检索 | 服务器统一管理材料、解析任务及检索 |
| 模型 | 本地模型或用户选定的云 API | 团队统一配置本地推理服务或云 API |
| 权限 | 个人工作区身份与业务动作规则 | 现有账号、岗位、案件、材料、财务及 AI 处理权限 |
| 后台任务 | 应用运行时处理，重启恢复未完成任务 | 服务持续运行，可集中处理与监控 |
| 备份恢复 | 应用内管理本机备份、导出、恢复 | 管理员备份数据库、文件、配置与必要密钥 |

桌面端可以设计“个人工作区”和“连接团队”两个入口。连接团队时以团队服务器为该工作区的数据权威来源；不默认把团队材料复制到个人库。个人数据迁入团队需要显式导入、身份映射和权限核对，不能把打开同一个文件夹当成多人同步。

个人版的安装目标是让应用完成初始化、启动和升级；后台可能仍有托管进程和模型运行时。机器关机时本机作业不能继续执行，持续提醒与后台处理由在线团队服务承担。

### 2.2 现有项目已经证明的交付模式

[AnythingLLM 官方对照](https://docs.anythingllm.com/installation-desktop/overview)明确区分单用户 Desktop 与支持多用户和工作区权限的 Docker 版本；其默认向量数据库为内置 LanceDB，嵌入模型也有内置选项。因此，RAG 产品可以把检索组件交给应用管理，不要求用户单独配置向量数据库。该事实不代表 LexOrder 已经具备同等能力，也不代表 AnythingLLM 的两种版本自动支持双向离线同步。[A1][A2][A3]

## 3. RAG 必须有，RAGFlow 是可选后端

### 3.1 RAGFlow 是否必须自行部署

**不必须。** 当前官方提供 RAGFlow Cloud；官网列出的 Starter、Pro 计划提供 API key，Free 计划不提供。也可以由团队集中部署一套，再由 LexOrder 服务端访问，成员无需逐台安装。套餐和额度会变化，接入时重新核对；本轮仅核实公开资料，未登录、购买或实测托管 API。[R1][R2]

RAGFlow 自部署仍是一套包含文档引擎、元数据、对象存储、任务和缓存等组件的服务。1.0 主后端改为 Go，并调整消息与缓存组件，仍不适合作为每个个人安装包的强制前置服务；安装器自动拉起服务也不会消除其资源消耗。[R2][R3]

| 路线 | 适用场景 | LexOrder 的定位 |
| --- | --- | --- |
| 内置 RAG | 个人安装即用，也适合集中运行的团队实例 | 推荐的共同基础能力 |
| 团队共享 RAGFlow | 需要其复杂文档解析、检索或编排能力 | 可选引擎适配，统一服务端管理 |
| RAGFlow Cloud | 希望减少服务运维，接受远程处理 | 可选托管连接器，明确外发范围与费用 |

### 3.2 内置 RAG 的完整范围

内置 RAG 应覆盖以下闭环：

1. **导入与原件保留**：校验文件、记录来源及版本，原件不被 OCR 或格式转换覆盖。
2. **解析与 OCR**：区分文本 PDF、扫描件、Word、表格；记录成功、失败、缺页及截断范围。
3. **分块与定位**：保留章节、页段和表格上下文，每个文本块绑定具体材料版本。
4. **建立索引**：中文关键词、规范化案号/金额/日期等字段检索与语义向量检索结合。
5. **授权范围内召回**：限定工作区、案件、材料及版本，合并候选并按需要重排。
6. **回答与引用**：模型根据所取材料生成内容；引用回到具体版本的原文位置，缺少依据时显示缺口。
7. **持续维护**：文件增删改、权限变化、模型或解析器升级触发失效或重建；任务可重试、可恢复。

向量存储只覆盖其中一部分。OCR、中文召回、引用定位、权限和增量一致性仍是 LexOrder 需要实现与验收的工作。

### 3.3 优先验证的嵌入式检索方案

**第一候选：LanceDB Embedded。** 它运行在应用进程内，支持本地文件存储，提供 Rust、TypeScript 和 Python SDK，以及向量和全文检索。其 Embedded 与 Enterprise 是不同运行形态，不能把企业版的分布式管理、授权和审计能力算到嵌入式库上。[L1][L2]

推荐先用同一检索适配器验证个人本机与单台团队服务器：个人由桌面核心调用，团队由服务端统一调用。团队用户增加不必立即换检索产品；多个服务节点、高可用与大批量并发索引需要另行验证存储所有权、写入协调和维护策略。

**备选：SQLite FTS5 + sqlite-vec。** 适合减少本机存储组件，但需要应用补齐混合召回和排序。sqlite-vec 当前仍是 pre-v1 项目；不能将预发布的 ANN 能力作为稳定大规模检索保证。FTS5 默认分词不能直接等同于中文分词，trigram 对少于三个 Unicode 字符的全文查询有限制；姓名、短词、案号等必须专项验证。[S1][S2]

**团队扩展候选：PostgreSQL + pgvector。** pgvector 可以把向量与业务数据放在 PostgreSQL 中，便于关联文档、案件与授权条件，也可减少独立向量服务。它仍需 LexOrder 提供完整 RAG 管线；这不是 RAGFlow 已验证的“一键换成 PostgreSQL”配置。[P1][R2]

本轮不要求同时实现三套引擎。先验证一个默认引擎，再按实际规模和部署需求增加适配；最终决定依据中文材料质量、安装复杂度、更新恢复及资源实测。

### 3.4 本地模型与云模型分别选择

| 模式 | 文本解析与索引 | 嵌入与重排 | 回答生成 | 网络与数据流 |
| --- | --- | --- | --- | --- |
| 完全本地 | 本机 | 本地模型 | 本地模型 | 所需模型与运行时准备完成后验证断网使用 |
| 本地检索、云端回答 | 本机 | 本地模型 | 云 API | 问题及被选中的材料片段发送给生成服务 |
| 云端嵌入 | 可仍在本机保存索引 | 云 API | 本地或云端 | 建索引及查询向量化涉及相应文本外发 |
| 团队集中处理 | 团队服务器 | 由团队配置 | 由团队配置 | 根据实际提供商分别记录外发，不能仅按“自部署”判断 |

OCR 如调用云服务，也会产生独立的数据外发。模型配置需要显示各阶段的执行位置；文件在本地不等于全部处理均在本地。

安装包应管理模型下载、校验、进度、离线导入和失败恢复，避免要求用户手工安装多个服务。模型文件可以按需下载，主安装包不必包含全部模型；完整离线问答仍需本地生成模型及其运行资源。

Cherry Studio 当前文档已经展示本地知识库、抽取文本与分块检查、召回测试、重新索引，以及下载后离线运行的嵌入/OCR 模型。适合参考其用户流程；部分平台不支持本地推理，不能由此推定 LexOrder 在所有目标平台都已可用。[C1][C2]

## 4. Rust 重构的职责与业务成本

推荐把 Rust 作为桌面与服务端共享核心的重点验证路线：

| 层 | 推荐职责 | 需要保留的边界 |
| --- | --- | --- |
| React 界面 | 复用成熟工作台、表单、阅读器和交互 | 当前 Next.js 服务端代码不能直接当作静态桌面前端打包 |
| Tauri 桌面入口 | 安装、窗口、本机文件访问、应用托管进程和升级 | 平台安装、签名、WebView 与权限能力需分别验证 |
| Rust 领域核心 | 业务规则、权限、状态变化、文档任务、RAG 编排 | 普通规则保持可读，避免为了框架抽象增加维护成本 |
| 团队 API | 认证、请求入口、调用同一核心 | 桌面 IPC 与 HTTP 只做入口适配，不各写一套业务规则 |
| 存储适配 | PostgreSQL/SQLite、原件及派生索引 | SQL 方言、事务、类型和迁移分别实现，不能承诺自动无损切换 |
| 模型与解析组件 | OCR、PDF/Office 解析、嵌入、重排、生成 | 可用成熟库或应用管理的辅助进程，以中文材料效果与打包可靠性选型 |

Tauri 官方提供前端适配与 Node.js sidecar 路线，因此可以过渡保留现有 TypeScript 业务服务；其存在不等于当前 Next.js 应用已经能原样变为安装包。[T1][T2]

**迁移业务逻辑会增加短期工作量。** 当前 Prisma 查询、事务内权限、数据库锁、金额精度、任务租约、NextAuth 会话以及 Word/PDF 处理，都需要有明确替代。Rust 的收益应体现在可测的资源使用、并发处理、安装维护和模块复用上；语言本身不保证 OCR 或生成模型更快。

实施时先提取行为规格与用例，再按模块迁移。短期保留 TypeScript 并配合 Rust 处理高价值部分，是允许的过渡路线。一次性全量改写、界面全面推倒、直接切数据库，均不是本轮已确定的实施动作。

## 5. 保留现有功能的迁移要求

以下是针对当前代码的评估重点，并非已完成适配。进入实现时须重新核对所选提交。[B1]

| 既有能力或约束 | 重构时的处理 |
| --- | --- |
| PostgreSQL 数组、JSON、Decimal、事务与行锁 | 显式设计 SQLite 的关系表、编码、精度和事务策略；SQLx/ORM 支持两种数据库不等于查询语义一致 |
| 数据库函数、触发器、CHECK 与部分唯一索引 | 建立对象清单，决定每项在哪层继续保证；仅迁移表结构不算功能等价 |
| 财务确认、应收核销、补充协议、审批 | 保留精度、资格、状态门禁、审计与幂等；单人使用也保留可追溯的确认动作 |
| 队列去重、租约、重试 | 个人版持久保存任务，团队版协调并发领取；长解析可续租或拆分，崩溃后可恢复 |
| 附件加密、版本与导出 | 保留原件、ID、版本、校验值及解密所需信息；备份包含必要配置和密钥恢复方案 |
| 索引、OCR 文本与缓存 | 同样纳入数据保护与清理范围；原件加密不能证明派生数据也已加密 |
| Word/PDF 模板与文书 | 用中文编号、表格、脚注、分页及引用样本核对；现有文档生态可暂时保留 |
| 模型连接与网络校验 | 本地模型提供商采用受控独立路径；当前界面中的 Ollama 选项不能当作本机连接已验证 |
| 升级与恢复 | 先验证副本迁移、数据核对、导出与恢复，再切换实际工作区 |

SQLite 为个人业务库候选，应用托管 PostgreSQL 为保留复杂数据库语义的候选；最终默认方案依据完整功能清单和跨平台安装验证确定。团队版保留 PostgreSQL，不要求团队成员安装数据库客户端。

## 6. 统一 RAG 的业务契约

以下接口与字段为设计约束，名称可在实现时调整。

### 6.1 原件和引用

- 复用 `Document`：一行对应一个具体版本，`familyId` 串联版本。块与引用绑定 `Document.id`、原件校验值及页段位置。
- `SourceAnchor` 表达 PDF 物理页/位置、Word 段落/字符等真实锚点；转换产物保留转换版本与映射。无法定位时明确标识。
- `DocumentIndexBinding` 保存引擎、索引代次、解析版本、分块版本、嵌入模型标识/版本/维度和同步状态。改变嵌入模型或文本后重建相应向量，避免旧向量对应新文本。
- 原件与业务记录为权威数据，索引可重建。原文事实、AI 提取候选、律师确认分别保留；事实时间线与系统操作日志分开。

### 6.2 权限与撤回

- 检索入口由 LexOrder 计算允许使用的材料范围；全文与向量两路都受范围约束，片段进入模型前再次核验。
- 能读取案件概况不自动等于能读材料全文、导出或向外部模型发送。沿用材料级及 AI 处理资格，不使用引擎工作区权限替代业务授权。
- 权限撤销、材料删除或撤回后，立即排除新检索与新模型上下文；后台清理索引失败可重试。缓存、历史 AI 结果、引用打开也复核当前访问资格。
- 撤回与撤权也使相关待执行及正在执行的 AI 任务失效；后续外发、结果交付与缓存写入前复核有效资格，发现失效时停止后续输出。已经发送或展示的内容不能承诺收回。
- 空授权范围在 LexOrder 直接返回空结果。RAGFlow `document_ids` 空列表表示不限制指定文档，不能把无权范围直接原样传入。[R4]
- 首个 RAGFlow 适配关闭 `include_knowledge_compilation`，或证明汇总片段的全部来源均获授权后再开放；引用了一个允许文档不代表汇总的其他来源均可见。[R4]

### 6.3 运行与交互

- 明确“已上传、解析中、部分解析、可检索、失败、待重建”等状态，实际覆盖不足时不显示全部处理完成。
- 用户可查看抽取文本、分块和召回结果，区分解析、检索、回答三个阶段的问题。
- 本地/外部引擎通过统一 `RetrievalProvider` 适配；解析、模型与 `LegalProvider` 分开，减少绑定单一平台。
- 对象更新与待处理任务可靠落库，任务以文档版本/处理代次去重；失败、取消、重试及模型升级有明确状态。
- 索引结果提交时核对材料有效状态及目标处理代次，过时代次不得覆盖当前状态。新代次构建完成后再切换可检索绑定，删除、取消或失效任务的迟到结果不得重新发布。
- `AiRun` 记录请求范围、实际读到的材料版本、覆盖与模型配置；AI 结果进入 `WorkProposal`，正式业务修改仍按既有权限与确认动作执行。
- 外部模型不可用时保留材料管理、原文查看及实际可用的本地关键词检索。语义检索、重排与回答生成分别检查依赖状态；查询嵌入或远程重排不可用时显示限制并按已验证策略降级，不能仅凭已有向量索引承诺离线语义检索可用。

## 7. 参考项目的核心逻辑如何进入 LexOrder

按“观察功能行为 → 提炼规则与输入输出 → 形成边界和验收场景 → 用 LexOrder 模型独立实现”的顺序吸收。下表记录研究方向，不登记为已复制源码或已完成集成。

| 参考 | 重点吸收 | 在 LexOrder 的落点 |
| --- | --- | --- |

## 8. 后续实施顺序与验收

### 8.1 分阶段推进

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| R0 决策落档 | 固定目标、区分推荐与待验证项、更新旧计划 | 本文及相关入口一致；仅文档完成 |
| R1 行为基线 | 梳理功能/权限/数据库守卫清单，准备经授权或合成材料 | 可按业务结果判断迁移是否等价 |
| R2 RAG 完整小流程 | 导入、解析、混合检索、回答、版本引用、撤回、恢复 | 同一组材料在个人与团队入口通过功能验收 |
| R3 交付原型 | 安装初始化、模型管理、团队部署、备份升级 | 用户无需手工维护个人版服务；团队集中配置可复现 |
| R4 分模块迁移 | 优先文档与 RAG 核心，再按风险迁移客户、任务等业务 | 每批保留行为、权限与数据核对结果 |
| R5 发布验证 | 目标平台安装/更新、真实业务流程、故障恢复和性能 | 明确支持范围与限制后发布 |

财务、审批、归档及其数据库守卫属于高耦合部分，迁移前先有完整行为基线。原计划的 12—16 周估算只针对原技术栈的增量路线，**不覆盖本轮 Rust、双交付与多数据库改造，不能直接沿用**。实施排期在 R1/R2 结果后重新估算。

### 8.2 必须覆盖的验收场景

1. 个人安装后可创建工作区，材料导入、任务恢复与索引维护由应用管理。
2. 本地模型及运行时准备后断网测试，OCR、建索引、检索和回答分别记录是否可用。
3. 云模型模式明确文本外发阶段；切换模型不会混用不兼容的向量。
4. 中文文本 PDF、扫描 PDF、DOCX、表格以及长文材料显示正确覆盖，失败有出口。
5. 案号、条款编号、姓名、金额、日期与同义表达均有固定召回样本；同时测试找不到依据的问题。
6. 上传新版本后旧引用仍回到旧版本；页码、表格和文字位置可核对。
7. 团队用户不能通过检索片段、回答、缓存、历史记录或引用打开无权材料；空权限范围不扩大查询。
8. 撤回、删除和撤权立即影响后续使用，索引异步清理失败可见并可恢复。
9. 中断进程、重复提交、重复领取任务不产生重复有效结果；过期任务可以重新处理。
10. 个人与团队共用的业务行为通过同一组输入输出用例；单人模式保留财务和审批的明确动作与留痕。
11. 恢复业务库、原件、必要密钥及处理配置，并确认所需解析器和模型可获取后，能够重建索引；缺少组件时显示待恢复/待重建，恢复当前授权状态后再开放检索。数据库切换前后 ID、金额、时间、状态与授权结果一致。
12. 记录冷启动、空闲内存、导入吞吐、索引时间、查询 P50/P95、峰值资源与任务积压；按目标硬件和数据规模比较，不先宣称 Rust 带来固定倍数收益。

以上均是待执行的验收要求。本轮没有启动服务、安装模型、执行数据库迁移或跑性能基准。

## 9. 待验证的决策

- 第一批支持哪些桌面系统及架构，安装、签名与更新成本各是多少。
- 个人业务库默认 SQLite 还是应用托管 PostgreSQL；完整功能差异和恢复流程是什么。
- LanceDB 在选定 Rust/TypeScript 正式版本上的中文分词、过滤、增量维护和打包是否满足需求。
- 团队初版复用嵌入式引擎的负载边界；何时需要 pgvector 或独立检索服务。
- 默认嵌入、OCR、重排与生成模型如何组合；普通设备的响应和资源表现如何。
- 保留多少现有 TypeScript/Office 处理代码作为过渡，哪些 Rust 模块先迁移收益最高。

这些问题通过原型与材料验收收敛，不阻碍已确认的“个人独立 + 团队自部署 + RAG 必备”产品目标。
