## 1. 已确认的产品目标

用户补充的[产品需求与验收基线](PRODUCT_REQUIREMENTS_ACCEPTANCE.md)是工程决策的依据：

- **恢复上下文**：目标、指示、事实、风险、最新决定、等待与下一步。
- **核查依据**：材料、法律来源、版本、反向证据与人工判断可以追溯。
- **落实责任与结果**：期限、任务、客户决定、复核、实际交付及费用相互关联。

首发聚焦中国大陆个人律师和小团队的民商事诉讼、仲裁，同时保留合同审查、顾问等既有事项类型。核心仍是 Matter，不因产品使用“法律事项”而更换数据身份。

首条完整验收流程：

**目标与指示 → 材料入库 → 事实与争点 → 带来源草稿 → 律师确认 → 行动与客户跟进 → 交付归档。**

全球律所招聘研究用于把研究、判断、表达、协作与交付能力内化为[专业技能](PRODUCT_REQUIREMENTS_ACCEPTANCE.md#10-技能是什么)。技能共用上述数据链，不能把产品简化成多个彼此独立的聊天助手。

| 目标 | 本轮决策 |
| --- | --- |
| Personal | 搁置、未排期；保留已有资产，不计入当前交付 |
| 部署与协作 | 可自行部署或代管独立实例，服务端集中鉴权与处理，普通成员只需浏览器 |
| 正式 release | Server 固定部署产物、核心业务、更新恢复；可选服务声明与实测分开 |
| RAG 与模型 | 内置处理/检索默认可用；RAGFlow、模型、OCR、法库/MCP 按需独立启用 |
| 保留业务 | 继续使用客户、收案、事项、权限、期限、财务、审批、文书和归档 |
| 技术主线 | Server 延续 TS/Next/Prisma/PG；不为搁置个人版重构当前部署业务 |
| 界面与性能 | 正文、材料和下一步优先；性能只观察、无硬阈值，不据此阻断发布 |
| 法域扩展 | 共用工作结构，分离语言、准据法、程序法域、机构、时区与处理地区；逐法域验收 |

内置检索不等于完全离线 AI：无模型时允许手工选材、编辑和确认成果，不产生伪造自动回答。SaaS、多端双向离线同步和多国规则同时上线仍不在首发。

## 2. 推荐的交付方式

### 2.1 当前 Server 交付边界

| 层 | 当前部署方案 |
| --- | --- |
| 使用/身份 | 管理员部署，成员浏览器使用；保留 NextAuth、岗位、会话撤销与业务审批 |
| 业务库/材料 | PostgreSQL 与私有 StorageProvider；保留迁移、金额和权限守卫 |
| 后台执行 | 现有 TS worker/JobQueue；领取 token、续租及条件发布，不新增平行任务系统 |
| 默认材料处理 | 内置解析与不可变覆盖/来源快照；无 OCR 的扫描页保持未识别，不影响原件操作 |
| 默认检索 | 现有授权 PostgreSQL 正文检索；向量/RAGFlow 按需启用，不伪称词法为语义 |
| 第三方能力 | AI、OCR、嵌入、重排、RAGFlow、法律 API/MCP 独立配置、懒加载和失败隔离 |
| 发行/恢复 | 固定 Server 镜像/配置、迁移、原件/密钥/数据恢复；只恢复实际启用服务的必要状态 |

所有外部服务关闭是合法配置。核心启动、登录、health 与普通业务不做外部探测；管理员“检查连接”和用户对应操作才触发调用。禁用、未配置、配置不可读、已配置未验证、可用、调用失败应分开；连接成功不等于工具或数据权益全部可用。

Personal 直接搁置，没有自动开始时间。下面 §2.2—§2.6 留作历史设计，不参与当前排期或门禁；其“必须/后续/M1/M4”只描述原个人方案的内部约束。

#### 当前轻量检索与业务解耦

实际源码 `ragflow-adapter.ts` 只提供上传、解析、查询和删除适配，当前构造调用在隔离验证工具中；`search/actions.ts` 已在 PostgreSQL 正文和当前材料资格上提供检索。A—F 的记录/模板/任务/期限/交付不导入 RAGFlow 适配器；它不能代替这些业务对象或审批。当前无需因暂缓知识发布而迁移检索引擎，也不为替代 RAGFlow 引入另一个大型服务。使用内置解析、现有授权正文检索、手工选来源和已有来源锚点；可选模型直接使用既有客户端。RAGFlow 完整部署与联调继续按需后置，未实连不宣称成功。正文词法检索不冒充向量语义检索；明确选择外部服务失败时保留错误和草稿，不静默切后端。

### 2.2 精简本地服务：先保留 Next，降低改造面

现有页面依赖 RSC、Server Actions、服务端读取、`next/cache` 与导航，事项详情还直接聚合 Prisma 查询。现在先改 React/Vite + 新 API/IPC，会同时重做数据读取、动作协议、刷新和运行上下文。采用现有生产 Next/Node，先抽取确需共享的领域服务；Personal 认证分离是本轮要求，不能因保留 Next 而保留登录流程。[B9]

具体实现顺序：

1. 为 Personal 构建 `output: "standalone"`，由打包运行时启动生成的 `server.js`；收集当前 `.next-build` 下静态资源、`public`、Prisma 引擎、迁移、模板与原生依赖。本批增加通过 `LEXORDER_STANDALONE=1` 构建共享根应用的入口，输出 `.next-personal/standalone`。它减少部署文件范围，不代表已证明内存下降；也不追加一层自定义 Express/Fastify server。[N1][N2][N4]
2. Personal 使用一个业务 Node 入口。现有 `run-with-cron.mjs` 会启动 Web 与独立 `tsx` worker，个人模式先复用 `instrumentation.ts` 的进程内调度，补启动、停机、休眠恢复和防重复；Server 保留现有分进程入口。不能让两条调度路径同时运行。[B8][B9]
3. 文本抽取中的 `mammoth`/`unpdf` 可移至格式分支按需加载；预览和 S3 已有部分按需加载，避免重复改造。重解析/OCR必要时使用按任务启动的子进程，不让子进程另开个人业务库。[B2]
4. 模板引擎拆分确有需要的边界：读取上下文、经确认写回、纯渲染。`applyOverrides` 有业务写入，不能整体当作纯前端工具。[B9]

M1 工程装配方向选为便携托管 Node + 共享 Next 根应用 + 系统浏览器 ZIP，不引入新 UI 外壳；Windows 原生依赖闭包、ACL、启动/关闭与实际产物尚未完成，当前没有 Windows ZIP 或安装包。正式安装按 M4 接续，个人版后续由用户验收。Electron 与 Tauri/系统 WebView 保留为此前研究的包装选项，未据此采用或证明平台可用。[E1][E2][T1]

### 2.3 嵌入式存储已开展验证：PGlite 优先

现有 schema 静态盘点：86 个模型、88 个枚举、20 个标量数组字段、26 个 Decimal、23 个 Json；五个迁移还包含 PL/pgSQL、触发器、CHECK、部分唯一索引。原始 SQL 使用行锁、advisory lock、JSONB 和 PostgreSQL 系统目录。它们涉及数据正确性，不能只改 `provider`。[B1][B5][B7]

| 方案 | 本轮实际判断 | 后续动作 |
| --- | --- | --- |
| PGlite + Prisma 5.22 | 保留 `postgresql` provider 和原迁移的有界试验已通过，优先进入个人适配 | 收口单连接所有权、私有通道、实际服务调用、异常恢复及目标平台发行 |
| SQLite + 当前 Prisma | 仅替换 provider/文件 URL 后，Prisma 5.22 校验产生 167 项错误；没有实施 SQLite 迁移 | 保留为备选，不并行重写数组/类型、锁、PL/pgSQL、金额和迁移。不能将 ORM 限制说成 SQLite 本身不支持 JSON/触发器 |
| 原生 PostgreSQL | 现有 Server 与兼容对照继续使用 | 若嵌入式正确性出现实质阻塞，再比较应用托管 PG；不要求个人用户手动维护数据库 |

### 2.4 PGlite 必须收口的正确性边界

PGlite 只有单数据库会话，socket 的多连接是复用，不等同普通 PostgreSQL 多会话。固定发布包仍包含公开问题 #1046/#1094 描述的消息交错及内部异常后队列停滞代码形态；本轮读取源码与 issue，**没有复现内部异常故障，也没有证明该故障已经解决**。[P2][P4][P5]

- Personal 由一个运行时拥有数据库目录与 PrismaClient，`maxConnections=1`、`connection_limit=1`。迁移、运行、备份分阶段独占。后台执行通过该所有者，不能每个 worker 各建“一个连接”的池。进程内事务只用传入的 `tx`，不占着唯一连接再等待全局 client。
- §2.3 的早期兼容试验使用 loopback socket、关闭 SSL 和语句缓存；URL 中的 `postgres` 占位值不构成访问保护。M1 已改为 §6.6 的随机凭据私有 PG 通道，不开放额外无认证端口；Windows 通道与正式产物未实现，不能由 Linux 局部试验推定可用。
- 历史 M1 私有通道 8 项反例通过，含认证前拒绝、分包、单会话、断连事务回滚和普通 SQL 错误后续用；引擎异常是注入反例，只证明该路径停止服务，不证明上游 WASM 故障已复现或解决。完整取消、异常退出、重启与恢复仍待个人版后续验收。
- `pg_dump` 会改变会话状态并清理预处理语句，备份前停写、断开业务客户端；恢复完成后重建连接。试验只移除导出中 `psql` 专用的 restrict/unrestrict 行，再用 SQL 导入，未改业务 SQL。不能复用现有原生 PG custom-format 脚本冒充 PGlite 备份。[P6]
- 单版数据库恢复不等于数据库+原件+配置+密钥的一致恢复，也不等于强制断电恢复。Personal→Server 需明确映射操作者、版本和文件哈希，并验证目标 PG 版本；不得共享数据库目录或假定 PGlite 18 的物理/SQL 导出可直接用于 Server PG 16。

这些是功能和数据正确性工作，不是性能门禁。当前证据足以选择一个优先方向，仍不足以宣称全部 PostgreSQL 行为或整个个人产品已兼容。

### 2.5 Personal 不建立用户认证体系

Personal 的首开流程是建立/打开工作区，可选填写姓名与联系方式，按需配置模型 API。没有登录、注册、密码、验证码、TOTP、退出登录、人员管理或账号切换。操作系统当前用户的工作区是使用边界；本机操作者仅用于作者、负责人、本人确认与审计，不承担登录功能。

| 改造点 | Personal 行为 | Server 行为 |
| --- | --- | --- |
| `src/lib/auth/session.ts` | 统一 actor resolver 从工作区取得稳定操作者；不读/签 NextAuth 会话 | 沿用认证会话及启用、权限、sessionVersion 检查 |
| `src/proxy.ts`、认证路由/页面 | 无登录重定向，认证/账号 actions 禁用，检查本地调用来源 | 保留现有登录和访问控制 |
| 下载/预览/导出 | 所有直接 `getServerSession` 的路径也改用 resolver | 仍按认证成员和资料资格授权 |
| Providers、导航、资料页 | 共享 actor context，不挂账号 SessionProvider；移除登录/退出/密码/用户管理 UI | 会话桥接同一 context，保留成员设置 |
| 业务确认 | 明确单人策略，真实记录本人复核/到账确认/交付，不伪造独立审核人 | 保留团队角色、审批路由与适用的自审批限制 |

运行模式只由可信发行配置及工作区类型确定；请求参数、Header、浏览器开关不能把 Server 切成 Personal。Personal 只监听回环地址，Host/Origin、写请求来源、Server Actions 与必要的应用通道校验仍保留；这不是让用户登录。密钥、文件与数据库操作留在本地服务。[B9]

保留现有 User 主键和业务关联：五迁移中有 67 条指向 User 的外键，责任触发器也读取有效操作者。Personal 当前搁置；此前以内部 email/passwordHash 占位维持旧结构的方案不再作为未来实施要求。若用户明确恢复此模式，按真实操作者模型与必要数据库迁移设计，不保留认证兼容层、不创建可登录管理员，也不让用户填写密码。明确本机能力策略，不靠 `SUPER_ADMIN` 放行所有业务。显示姓名变化不改作者 ID；迁往 Server 时保留原作者与本人确认性质。[B1][B9]

#### Personal 的逐项业务确认策略

W01.2 先形成下表的服务动作清单，W17.1/W17.2 实施；策略来自运行模式与工作区能力，不是可登录角色或请求中的开关。每条路径仍校验输入、对象/版本、状态、幂等和审计。

| 动作 | Personal 必需行为 | 保留的业务条件 |
| --- | --- | --- |
| 收案及转正式事项 | 同一操作者提交并明确作本人确认，实际记录冲突核查与选择 | 主体/范围、冲突结论、必要资料与转化幂等，不造第二审批人 |
| 文书复核 | 对确切版本执行本人确认，保留待确认/已确认及修订记录 | 新版本不沿用旧确认，引用/缺项核查与原件版本保持 |
| 到账与相关财务确认 | 登记仍进入待确认，再由本人显式确认；作者和确认动作分别留痕 | 金额精度、核销/退款/结算和数据库守卫不变；不因个人模式自动认定到账 |
| 结项与归档 | 本人确认本地归档规则/版本、完整性与归档快照，再执行适用动作 | 未完成工作/待确认款/材料缺项等原有条件继续检查，归档旧包不改写 |
| 必要配置 | 工作区设置可维护模型、备份、模板及归档规则，采用明确的本机配置能力 | 不要求账号、岗位或管理员初始化；不借用 SUPER_ADMIN 放行所有业务 |
| 团队专属流程 | 不显示或执行人员管理、多人责任移交及确需他人资格的流程 | Server 独立资格/审批/用章规则不被个人例外修改，不伪造其他人的批准 |

此表细化已定单人策略；实现时将现有服务逐项映射并验证，不能只移除登录页。个人→部署迁入如以后实施，原本人确认性质必须保留。

### 2.6 安装、生命周期与恢复

首个目标为干净 Windows x64 普通用户环境；macOS/Linux 只在实际机器与架构完成后列入支持。目标用户不预装开发工具，安装包包含必要运行时或由安装器明确托管。M1 的 W03.2 就生成最小 Windows 托管包，验证运行时/Prisma/PGlite/LanceDB 加载、中文路径、单实例、本地通道与重开；M4 再对最终安装包执行完整流程及更新恢复，不能把目标平台风险全部后移。

- 验证中文/空格目录、数据与程序分离、重复启动、原生模块和 Prisma/OpenSSL 兼容；Linux 试验不能代表 Windows 包已可用。[E2]
- 桌面外壳最小权限，远程团队页面不能取得个人工作区文件/数据库能力；Electron 使用 context isolation/sandbox，关闭渲染器 Node integration。[E1]
- 迁移独占、失败回滚/恢复副本、更新和卸载保留数据；嵌入式库升级与应用版本分开管理。Server PostgreSQL 大版本按既有升级流程处理。[P1][P7]
- 本机关闭/休眠时作业暂停；唤醒补扫、恢复和去重。现有启动补扫仅在计划时刻后 15 分钟内，不能当作完整离线恢复。[B8]
- 备份覆盖数据库、原件、配置与可恢复密钥，形成一致恢复点。恢复后先重建正确的工作区/访问边界，再开放检索。持久性错误不能因取消性能门禁被忽略。

开发运行器 `tools/cloud-dev/run.mjs` 和现有 Web/worker 监督器只作已有基础，不直接当个人安装器。[B6][B8]

### 2.7 性能仅作观察

不设最低内存、启动秒数、CPU 或吞吐通过阈值，也不据此改变 release 状态；尚无测量数据也不阻断功能开发或发布。发现问题可继续优化，是否进入正式性能门禁由后续明确决策决定。

如进行观察，记录真实设备/系统、发布构建、完整进程树、工作包规模、模型位置与配置。区分基础业务、材料处理、可选本地模型；记录启动、内存、CPU、耗时与磁盘占用，不用开发服务器或 Node heap 代替完整应用结果。硬件与模型占用不能混成普通客户端的最低配置承诺。本轮没有性能实测结论。

## 3. RAG 架构：内置优先，服务可选

### 3.1 内置业务基线与可选后端

Server 先复用现有内置解析与 PostgreSQL 正文搜索，将原件、解析代次、覆盖、来源及权限接入真实工作台。现有 `parseMaterial`、LanceDB 和 RAGFlow 原型的边界分别记录；不为连接业务额外引入向量数据库。

`RetrievalProvider` 与来源契约不因可选后端改变。只在明确选择并启用服务时调用它；未配置或失联返回该能力的状态，不阻断普通业务，也不静默扩大范围或把空回答记成功。向量或生成需要相应模型配置，不能因生成模型存在就推断 OCR/嵌入就绪。

| 能力 | 默认路径 | 可选增强 |
| --- | --- | --- |
| 原件/版本/权限 | LexOrder PG 与私有材料存储 | 不转移权威身份 |
| 解析/覆盖 | 内置 PDF 文本层、DOCX、TXT、基础 XLSX；扫描未识别明确可见 | 独立 OCR 或 RAGFlow，按服务配置与逐件资格调用 |
| 检索 | 现有授权正文/关键词搜索，人工选择原件与片段 | LanceDB 原型按实际需要复用；可配置 RAGFlow/嵌入/重排，未验证不宣称可用 |
| 成果 | 人工编辑、来源校验、确认与保存 | 配置生成模型后生成候选，仍须人工确认 |
| 法律来源 | 用户提供且获授权的法律资料 | 官方法律机构 MCP/API 目录与自定义远程连接 |

Personal 的 LanceDB 打包与单实例设计随个人版搁置。其历史 SDK/中文 FTS 试验只证明相应组件，不证明部署应用已集成语义能力。

### 3.2 共用来源契约，三类资料

| 范围 | 业务意义 | 首发要求 |
| --- | --- | --- |
| 当前事项材料 | 支持事实、陈述与证据分析 | 具体 Document 版本、锚点、覆盖与材料/AI 权限 |
| 获授权法律资料 | 支持法律规则与分析 | 法域、来源类型、效力角色、相关日期、有效期间、检索时间、原始 ID/链接与实际权益 |
| 个人/律所经验 | 支持方法与模板复用 | 显式选入、脱敏、审核、适用条件、受众、版本和失效状态 |

可以共同检索，但输出须说明来源性质。经验库不自动吞入所有历史案卷；同一律所不等于全部成员有权访问全部案件。

法律服务复用现有元典/cncases HTTP 入口，并加入官方 MCP 预设与自定义远程 MCP。官方说明、真实 endpoint、认证、能力发现和实际调用分别登记；没有可核实官方 MCP 的机构不编造端点。未配置不阻塞研究、交付或发布；启用后按实际查询/片段/缓存/再处理权益使用。

### 3.3 处理、检索、回答是不同阶段

原件保存 → 页/段/表格解析与 OCR → 分块 → 词法/向量索引 → 权限内召回 → 引用与覆盖快照 → 生成候选 → 律师复核。

这些阶段适用于当前 Server：先内置处理，再按选择启用服务。RAGFlow 启用时仅通过受控解析/检索接口取回片段，由 LexOrder 复核权限、版本和覆盖，不直接把第三方 Chat/Agent 输出登记为已确认事实或成果。

本轮 W05 已将逐单元内置解析接入事项材料的持久上传与后台任务，覆盖文本 PDF、DOCX、TXT 和表格；扫描页在未启用 OCR 时保留未识别范围。短信 OCR 与传票首页解析保持各自范围，不能把局部能力或模拟 provider 写成真实通用 OCR 已完成。实现契约见 §6.4.1，实际验证见计划 §8.4。[B2][B8]

现有 AI 文书审查有分段、截断和数量限制，仍包含请求内执行；新增工作要补真实阅读覆盖和可恢复作业。检索到若干片段不等于读完全部案卷。[B3]

### 3.4 Server 按需连接独立模型 API

模型服务与应用运行位置分开配置，并独立于应用启动。Server 可选公网、明确受信内网或本机独立服务；不捆绑权重/GPU。Personal 的对应约定保留但不实施。

| 能力 | 配置与判断 |
| --- | --- |
| 生成 | endpoint、协议适配、模型 ID、凭据、上下文限制、超时/取消、流式/结构化能力；不能假定任意 API 完全兼容 |
| 嵌入 | 可选另一 provider/模型；记录维度及完整模型/预处理指纹，改变后建新索引代次 |
| 重排 | 按需配置，明确未启用/降级状态，不强制依赖某家服务 |
| OCR/视觉 | 单独声明图像/文件输入能力，原图与文本的外发范围分别提示 |
| 配置验证 | 按实际能力分别连通测试；401/403、超时、限流、不支持与无检索结果分开；不暴露明文 key 到浏览器或日志 |

**Server 分开管理各项可选服务。** RAGFlow endpoint/key 不等于生成模型配置；其解析/嵌入/重排仅在启用该后端时按真实生效配置登记。只换生成模型不自动重建索引；影响解析/分块/嵌入时生成新代次。任何一项缺配置不影响其他项和普通业务。

公网 URL 校验保持现有防护；自建内网/localhost 采用独立受信端点策略，限定配置地址/端口和重定向，不全局放开 SSRF。需要 key 和可无 key 的本地服务按 provider 声明处理。Server 容器里的 `localhost` 指该容器，不是浏览器用户电脑，配置说明必须表达清楚。[B4]

| 运行档位 | 能力范围 |
| --- | --- |
| 基础本地工作 | 个人事项、材料、任务、模板与已有记录不依赖模型；模型断开保留普通业务及已验证关键词搜索 |
| RAG + 独立模型 API | Server 默认内置解析与 PG 正文检索；选择启用时接 RAGFlow 与所选模型协作；分别说明向 RAGFlow、OCR、嵌入、重排和生成服务发送的内容，不称完全离线 |
| 按需本地组件 | 用户另选本机嵌入/OCR/推理服务；组件未运行时明确不可用，不默认常驻或增加硬件门槛 |
| 全离线 AI | 指定并准备所有必要模型/运行时，在实际断网下验证后才声明；已有向量不代表查询嵌入已可离线 |

首发优先让独立 API 可配置可用，不以建设模型商店或下载器为前置。未来确需托管模型下载时，再补完整性、存储、停止/卸载和离线导入。AnythingLLM/Cherry 可作体验参考，不证明 LexOrder 已完成集成。[A1][A2][C1]

### 3.5 Server 的 RAGFlow 接入与运维边界

首个联调目标固定为正式版 **RAGFlow v1.0.0**（2026-11-06 发布，标签提交 `db1cd59`）；实际发行锁定镜像摘要及其依赖清单，不跟随 main、DEV 或 latest 自动升级。TS 经版本化 HTTP API 接入，同时检查 HTTP 状态和业务 `code`，区分内置解析与自定义 pipeline 的接口，不沿用已移除的旧别名；RAGFlow 的实现语言不改变业务主线。[R1][R2]

1. **部署与访问**：RAGFlow 为可选配置，默认禁用，不加入核心启动 `depends_on` 或全局健康门禁。管理员可选择已有兼容实例或单独启用配套部署；普通成员只用 LexOrder，不发放服务密钥。未部署/未配置不阻止应用启动和本地处理。启用后仍单独管理其持久化与版本。[R4]
2. **任务与身份映射**：LexOrder 保存 `Document.id + sha256`、后端/实例、dataset/document/chunk 映射、解析与嵌入指纹、代次、远端作业状态和覆盖。按事项/资料范围与配置代次组织数据集，材料级权限仍逐件计算。TS 队列负责可靠投递、状态核对和取消，投递前复核材料资格、版本及外发范围；RAGFlow 负责解析/索引执行。上传超时先核对远端结果，避免盲重试形成重复或孤立材料。W04.3 必须实测固定版本支持哪种查找/关联方式，并把本地操作意图与可核对标识交给 W05.3；不预设服务支持任意幂等键。无法确定远端是否已创建时进入待核对并给出运维核对出口，不盲目重传或宣称取消完成。只有当前代次通过来源映射和覆盖检查后才开放检索，不把已接收任务等同于已处理完整。
3. **检索前后授权**：LexOrder 计算当次允许用于 AI 处理的具体文档白名单并映射远端 ID；空白名单在本地返回空，绝不向 RAGFlow 发送可被解释为全库的空筛选。检索请求显式携带允许的 dataset/document 范围；返回片段在进入模型、界面、缓存与历史前再次检查资格、版本和代次。RAGFlow 的 Only me/Team 规则不替代事项与材料权限，普通成员不通过其原生共享入口绕过 LexOrder。[R2][R3]
4. **汇总与高级检索**：首发显式设置 `include_knowledge_compilation: false`，使用可追溯原始来源片段。1.0 的文档筛选不能证明某个数据集汇总的所有来源均获授权；未来启用必须检查全部来源。该版普通 retrieval API 的 `use_kg: true` 也不代表多跳图检索已启用。Knowledge Compilation、Agentic Chat 等只在来源、工具权限与技能验收完成后接入，不因部署平台就默认开放全部能力。[R1][R2]
5. **引用与材料状态**：远端 chunk ID 只作技术映射，引用始终回到 LexOrder 的具体原件版本与 SourceAnchor；无可靠页段位置时明确限制，不猜页码。RAGFlow 内的块编辑、重解析和分块变更形成新的派生代次，不改原件、不使旧引用漂移；首发通过受控管线维护派生结果，不向普通成员开放绕过版本记录的管理编辑。
6. **撤回、删除与失败**：成员撤权首先在 LexOrder 即时生效，进行中结果、缓存、历史与引用重新核验；不因某成员撤权而删除其他成员仍获准使用的材料。材料整体撤回/删除时，LexOrder 立即禁止新的提交、召回、结果展示及自身发起的外发，并可靠投递远端取消/删除。远端处于“取消待确认/删除待确认”时如实显示，确认前不得宣称远端处理或全部外发已停止；迟到结果不得发布，已外发内容不能承诺收回。RAGFlow 断连时保留普通业务和已有原文，明确显示解析/检索不可用及恢复入口，不悄悄切回另一索引或扩大查询范围。检索失败或解析未完成时，不以无材料生成冒充成功的材料分析。
7. **恢复与迁移**：备份包含业务库、原件、必要密钥/配置/绑定、已启用 RAGFlow 的必要元数据与无法从原件重建的派生记录；可重建索引记录所需版本与配置。恢复后先核对当前权限及版本映射，再开放检索，不能只恢复 LexOrder PG 就宣称整套 Server 已恢复。Personal → Server 迁入搁置；未来如实施，应迁入原件、业务记录与稳定引用后按 Server 管线重建索引；不直接复制 LanceDB 向量目录作为 RAGFlow 数据。导入范围与操作者映射另按实际支持验证。

### 3.6 首发能力与后续扩展

Server 本期须完成材料导入/真实覆盖、来源/原版本、手工成果与错误恢复。中文语义、通用 OCR 和真实自动生成按实际启用能力另验，不用精确查询或人工结果冒充。Personal 不在当前验收范围。

RAGFlow 的解析、管线和高级检索作为可选增强逐项使用；不复刻其管理平台或 Agent 画布。无服务时内置业务继续，无法处理的页或格式如实说明。

当前维护 Server 内置业务和可选外部适配，不追加无需求的通用后端切换平台。Personal 运行/存储/索引打包搁置；未来恢复需另行明确。

## 4. 为什么 TypeScript 是当前主线

| 比较项 | 保留 TS / Next / Prisma | 全面 Rust 迁移 |
| --- | --- | --- |
| 业务规则 | 增强已存在服务与事务 | 重写并重新证明状态、金额、审批、权限行为 |
| Web 界面 | 保留 RSC、Server Actions、会话与页面 | 重划接口与鉴权边界，适配页面调用 |
| 文档生态 | 复用现有 DOCX、PDF、表格、模板工具 | 验证替代库或仍需辅助进程 |
| RAG | 共用 TS 编排；Server 默认内置解析与 PG 正文检索，按需经 HTTP 调用 RAGFlow；Personal 搁置 | 编排本身需重写，OCR/模型速度不因语言自动改善 |
| 交付成本 | 新增桌面托管与安装工程 | 同时承担语言、接口、数据库与交付变化 |
| 当前决定 | 作为持续业务主线 | 暂停整域迁移，按局部测量结果重新评估 |

这是针对当前仓库资产的成本/风险判断，尚无可据以报告的开发速度倍数或性能对照数据。

重构的重点是：从请求入口拆出可复用业务服务、统一材料处理和引用、补齐可恢复任务、接通工作链。按正在修改的功能逐步提取，不先全仓搬目录，不引入新的通用 ORM/工作流框架作为前置。

Server Actions/Route Handlers 通过统一 resolver 取得本机操作者或认证成员，保留输入校验和页面刷新；业务服务接收显式 actor/context，事务内按运行模式复核适用权限、状态与版本；worker 调用相同服务。Personal 移除账号认证，仍保留业务确认和工作区边界。

Rust 的后续使用条件：已知热点经 profiling 证明是本模块 CPU/内存问题，成熟原生库或任务拆分仍不能解决已确认的问题；或某项原生集成确有收益。性能当前不作阻断条件。以小接口替换该组件，再跑同一验收包。

### 6.2 权限、版本与确认

1. 全文、向量两路都使用服务端计算的授权范围；空范围直接结束。送入模型、输出、历史读取与打开引用时复核当前权限。
2. Server 的案件概况、材料全文、AI 处理、财务、审批和导出分别授权，团队汇总或系统管理员不替代业务资格。Personal 用本机工作区能力和单人确认策略，材料撤回、外发意愿、版本与正式写入确认仍有效。
3. 文档/权限撤回后，LexOrder 内立即阻断相关任务的后续投递及结果发布；后续外发、结果交付及缓存提交再次核对。Server 已投递至 RAGFlow 的任务按第 3.5 节确认取消/删除状态，不把本地失效视为远端已经停机；已经发送的内容不能承诺收回。
4. 引用绑定具体版本与锚点。新版本提示受影响的分析/文书，旧引用不静默改指最新版本。DOCX 用真实段落/字符或转换映射，无法定位时明确说明。
5. 解析代次绑定原件和解析器版本；实际启用向量嵌入时，索引代次另绑定分块版本、嵌入 provider、模型 ID/修订、影响嵌入结果的输入配置和维度组成的完整指纹。同维度不代表向量兼容；配置切换须建立新代次，完成后原子切换，不混查不兼容向量。删除、取消或旧代次迟到不得重新发布；验收覆盖模型切换及重建失败。备份权威数据及必要组件后，索引允许重建。
6. AI 输出是候选。通过类型与来源校验、人工复核，再由既有业务服务写入；事务内复核操作者、目标版本、幂等与状态。
7. 草稿生成、内部审核、正式提交/交付和客户确认分别记录。技能默认形成可审阅成果，不凭模型输出自动承诺、付款、发送或提交法院。
8. 当前历史 AI 成果与缓存始终核当前访问资格；未来如另行恢复知识发布，须单独设计显式选入、脱敏、审核和受众。后者不是本期实现或验收前置。
9. 材料版本/处理代次变更与任务意图须同事务落库，或同事务写 outbox 再可靠投递，并有补扫。原件文件不与业务库共事务：先持久化 `MaterialIngestIntent` 和恢复作业，再使用预留、不覆盖的对象键保存原件并确认，最后在同一事务建立 Document、解析运行/任务及审计。恢复仅核对该意图绑定的原件、大小和指纹，不扫描全库；迟到回执不能回退已提交状态，放弃上传保留审计。原件未就绪不得进入解析、召回或正式成果；不覆盖旧版本原件。W05.1 分别验证文件保存→DB 提交及 DB 提交→任务投递两个中断窗口。
10. 当前 Server 恢复协议在 W05/W13 开发；Personal/W17 的恢复设计搁置：停止新投递，形成数据库/原件/必要配置与后端状态的一致恢复点，保存有效代次和待核对远端作业；恢复到隔离工作区/实例后先校验权限、版本与绑定，隔离旧会话/作业结果，再开放检索。Server 远端仍可能处理中的任务要核对，不以暂停 TS worker 代表 RAGFlow 已暂停。备份后的授权撤回不能被旧快照静默放大；无可验证当前授权状态时保持受限并由真实管理员核对。

### 6.3 技能如何进入 TS 架构

### 6.4.1 Server M2 本批数据与接口（冻结及实际实现）

- `MaterialIngestIntent`：先持久意图和恢复任务，再写预留对象键；记录提交者、事项/收案、版本前件、元数据和原件身份。COMMITTED 不得回退或改绑，UPLOAD_ABANDONED 为关闭终态；迟到回执只做条件更新，恢复仅读取对应原件。
- `Document.parseGeneration`、`DocumentParseRun`：按原件版本递增处理代次；历史 coverage/anchors 发布后不覆盖，textContent 仅是当前搜索投影。无 OCR 的扫描页保持未识别。
- `JobQueue.leaseToken`：领取/续租/完成/失败均带本次 token；发布事务锁定并核验租约、代次和当前权限。`assertCurrentJobLease(tx, {id, leaseToken})` 与 `renewJobLease(...)` 由队列单一 owner 提供。Prisma 无时区时间列的租约比较明确使用 UTC，不依赖 PostgreSQL session 时区。
- `EvidenceItem.revision` 与 `EvidenceItemRevision`：编辑正文/性质或增删来源前快照旧正文、来源关系和当时确认，再推进修订并清除确认；快照不得覆盖。
- `EvidenceSourceLink`：同一 EvidenceItem 关联多个具体 Document/hash，关系为 SUPPORTS/REBUTS/CONTEXT；原件页或无法定位先可用，再关联不可变 run/anchor。撤销保留记录，读取/打开分别检查材料权限。
- `MatterContextRecord`：GOAL/CONSTRAINT/INSTRUCTION/OPTION/DECISION，线性版本链、作者、原来源、待确认/已确认、财务可见性与请求幂等；更正生成新版，不覆盖正文或继承确认。MatterBrief 为授权聚合，不复制权威状态。
- `enqueueMaterialProcessing(tx,{documentId,requestedById,expectedGeneration?})` 同事务建代次和队列意图；`processMaterialJob(payload,lease)` 复用现有解析器；状态与历史来源动作只返回当前有权读取的内容。
- 原件提交、恢复、撤回和清理由 `material-ingest.ts` 接持久队列；历史来源、审批、归档或收案快照引用的原件受保护。清理保留数据库墓碑和审计；旧正文回填只处理 parseGeneration=0，不能覆盖新代次。
- 可选服务配置复用 SystemSetting 与加密凭据；MCP 采用远程 HTTPS Streamable HTTP，当前由管理员显式配置、检查、发现和手动只读检索；普通用户的事项研究入口尚未接入。不开本地任意命令，不自动执行发现到的写工具，不自动外发整案材料。

### 6.4.2 M2 连续记录与事实日期增量合同（2026-11-16）

- 客户历史复用 ClientActivity、ClientFollowUp、Note、Intake、Matter、MatterContextRecord、联系人及获准已确认财务记录；不增加平行事件表。事项计数与列表使用相同关联/可见过滤，沟通资格单独检查，财务主档读取不等于沟通读取。聚合按稳定业务时间/来源/ID 排序，游标不能承载权限条件；空页、失权、删除及更换客户均有明确出口。需要跨过不可读来源的扫描位置使用域隔离、绑定操作者/客户/列表的 AES-GCM 不透明游标，密钥从既有 NEXTAUTH_SECRET 派生；签名或 base64 不作为隐藏日期/ID 的保护。
- 指示/决定通过 context 服务的内部授权呈现接口读取，输入仅为已归组的记录 ID；函数重新限定事项与财务范围并检查当前原件、Note 或客户沟通来源。聚合不能直接下发 raw ContextRecord，也不通过隐藏行的数量或日期泄漏内容。
- EvidenceItem 和 EvidenceItemRevision 同增 `EvidenceDatePrecision` 及日历日边界/原始表述。数据库 CHECK 约束精度组合、日期顺序、有效范围和原文长度；旧行默认 UNKNOWN，不补造发生日。历史不可变触发器继续覆盖新列。日期变更走同一 revision/确认/来源守卫；接口以完整 `eventDate: {precision, start, end, text}` 对象传输，外层缺省的旧更新调用保持当前日期，局部残缺对象拒绝。
- 时间线只读取授权后的 EvidenceItem 视图；未知单列，同日次序仅用于稳定显示，不推定事件先后。区间保留两个端点，来源受限时整个日期对象为空，历史同样处理。共享事项页仅提供入口，编辑/确认/原件操作继续复用原组件。
- 本节合同已在代码候选 `da2701b` 实现；新增迁移、7 个真实 PG 场景、两组开发模式真实会话 HTTP 和生产构建结果见[计划 §8.6](WORKBENCH_PLAN.md#86-m2-连续记录与事实日期执行结果2026-11-16)。该批实际浏览器曾阻塞；后续真实页面操作与修复单独记入计划 §8.7/§8.8，不把旧 M2 测试结果自动扩展到新增分页或时间线。

### 6.4.3 用户页面反馈的路由与摘要接线（2026-11-16）

- 当时的路由修复采用实际 `internalCode`/历史 ID 精确匹配及唯一大小写后备；这是已有实现和验证记录，用户新增“不保留兼容/fallback”后不再作为保留要求。现行目标见 C02：仅按完整实际 `internalCode` 生成和解析案件地址，移除旧 ID、大小写后备与缺编号退 ID 的分支；所有现行入口一起更新，数据库主键及业务引用不变。解析仍不授予权限，页面继续执行 `getMatterById` 与原业务/团队访问检查。
- 原详情 archive 视图命名为「档案与摘要」，调用现有 `getMatterBrief` 获取当前授权聚合；组件按事项和刷新标识隔离响应，重新读取时清除旧结果，失败可重试。摘要来源受限的正文不下发/不展示，既有服务和记录保持权威；不引入 AI 或第三方启动依赖。
- 原 work 视图命名为「办案与材料」，材料/证据/时间线仍只在该业务区域维护；管理导航统一「AI 与外部服务」。团队概况只有当前会话具备 `schedule.read` 才调用 Note 列表，无该资格时不把读取失败伪装为无记录，也不授予材料、财务或写入权限。
- 无 schema 或迁移改变；本轮定向测试和原报错链接的真实浏览器复验独立记于计划 §8.7，历史 PG/HTTP 不重跑。

### 6.4.4 离线输入范围与界面动作增量（2026-11-16）

- `getMatterInputCoverage` 接受明确事项及最多 50 个唯一 `Document.id`，可指定该材料的历史 `parseRunId`；空选择不查询材料。只读取具体版本的持久解析快照，不读原件、不重算 hash、不写 DB、不调用模型/检索服务。默认只读当前解析代次，正在处理时不悄悄回退旧代次。
- 读取前后分别复核有效账号、`documents.read`、逐材料读取资格、事项关联和具体版本；准备审查范围另需材料处理资格及 `documents.write`。最终重新读版本/代次，失权或变化的材料只回显调用者原 ID 和 `UNAVAILABLE`；预算在最终权限过滤后分配，隐藏对象不消耗可见对象预算。
- 每次最多准备 36,000 个 UTF-16 代码单元，按请求材料顺序、单元/锚点顺序取前缀，不拆代理对；范围是不可变 `anchor.text` 内的半开区间。文本范围明细与处理单元明细各最多 200 条，省略数量独立保留，统计不冒充完整展示。返回处理状态和范围位置，不返回正文；`modelSupply=NOT_SENT`、`sentChars=0` 固定。
- 新 UI 只作用于明确勾选的本页程序材料，不跟随上方环节筛选，也不扩大为自动全案。服务端页面刷新标识重置旧选择与结果；切换对象、选择、失败或迟到响应不得留下旧诊断。入口不依赖 AI 配置，不改既有 ReviewRecord、不虚构 AiRun；真实模型供给清单和候选处理记忆后续独立实现。
- 原统一编辑弹窗增加目标分区，案件/程序/当事人/团队入口遵守原字段资格并定位相应区域；无程序不显示无法编辑当事人的假入口。目标指示、来源、版本历史分别保存触发焦点，嵌套返回回到对应上一层。`ConfirmHost.initialFocus` 是可选参数，默认行为不变，目标/指示与事实核对明确使用取消初焦点。
- 同日来源只在原权限查询内增加时间、短内容摘要及文档版本标签。事实 UI 把版本状态称为「记录核对」，不改数据库确认字段、性质枚举、修订守卫或法律事实判断。上述为界面与读取增量，无 schema/迁移变动。

### 6.4.5 人工创建要点的重试合同（M2 收口）

事实复核发现首次创建缺少请求身份；事务串行和按钮 pending 不能避免“已提交但响应丢失”后的重复创建。此项属于原 W06.2 幂等要求，复用既有 EvidenceItem，不引入候选或 AiRun 模型。

- 新建动作要求调用者提供 UUID `requestKey`；一次表单打开及其失败重试保留同一键和草稿，关闭重开或换事项才产生新键。用户修改草稿不自动换键；若原请求实际已保存，同键异载荷明确拒绝，防止悄悄生成第二条记录。
- EvidenceItem 增加可空 `requestKey`/`requestHash`，以作者+键唯一。旧记录两项保留 null，不补造历史请求；新数据成对保存并有格式约束。创建身份和指纹不可被后续编辑清空或改写，来源、修订和审计继续使用原对象。
- 指纹由服务端已校验、trim 和缺省归一的固定创建字段计算，包括事项、标题/正文/性质、完整发生日期和来源 ID/页/关系；不含 key、当前 revision 或可变解析内容，不重算原件 hash。匹配的重放返回原 ID；异载荷拒绝，不新增原件关系/修订/审计，也不回滚已编辑或核对的要点。
- 每次重放在新事务内重新检查当前操作者、事项可写和来源资格。保留 Serializable；序列化冲突及明确的作者/请求唯一冲突只作有界整事务重试，其余唯一冲突不当作成功。并发请求必须收敛到同一正式记录。
- 模型/SQL、服务和创建表单已分开实施并二轮定点审查。root 统一应用增量迁移、验证新增 4 项真实 PG 和最终构建；预览库原 5 个要点/4 条修订升级前后保留。服务与表单局部证据、原页面保存/重开结果见计划 §8.9，没有重跑既有来源/日期全套。

**C06 补充：** 所选批准版本以具体Document ID、未撤回、所见updatedAt和APPROVED核对，不擅自追加“必须为上传人/必须是同族最新版”的新入卷资格。所有岗位在同一tx内复核账号、角色、案件关系和归档状态，保留已固定收案送审原件保护，状态改变与DOCUMENT_FILE审计同事务；并发或重复请求不能再次产生成功事件。本人确认分支命中既有清单时不要求独立审批路由；该例外不扩展到开票/归档。退回而未修改内容的原草稿仍可按既有条件重提，不自动复制新版本。

**C07 补充：** 指纹来自服务端校验归一的原始创建载荷，包含案件/无案原因、Decimal金额、票种/名目、购方字段、备注及去重排序后的具体依据ID；不含后续审批/开票/处理字段，不能从后来变化的业务记录反算。身份/指纹后续不可清空或改写。每次请求核当前有效操作者及访问资格；只有不存在既有申请时执行完整创建前置。获准的同键同载荷重放返回原ID及当前状态，不重置已批准/已开票结果，不重发业务事件或通知。并发由真实事务与数据库唯一约束仲裁，只将requestedById+requestKey的确切唯一冲突识别为重放，其他错误不伪装成功；读取既有结果不等于再次执行创建。

**C09 补充：** 来源守卫覆盖新结果落库/回传、历史列表/详情和报告保存，不能只在“保存”按钮核验。调用后来源已撤回或操作者失权时，迟到结果不得发布可见成果。报告 Document 持久保留不可变 ReviewRecord 与具体来源版本关联；重开/预览/下载及正文读取复用同一来源检查。缺可信绑定就明确不可用，不能降级普通材料放行，也不通过名称/正文/标签猜测；不新增旧报告适配器、待恢复队列或来源恢复工作台。必要存量结构处理须先核实数据，再用明确数据库迁移，不能补造事实；无法核验的历史范围仍登记未通过，不用新报告验收覆盖。历史覆盖未记录则如实显示，不填虚假数字。集成人仅协调这条实际链所需的 Document/ReviewRecord 关联和现有读取入口，不引入完整 AiRun、平行报告身份或通用派生产物框架。

框架基线实际为 Next/React、Tailwind 3、shadcn `default` 与 Radix；项目 Button/Badge 已映射 LawLink/墨案主题，优先使用其现有 variants 和 patterns。官网新 API（如新增关闭参数、Field/Empty/Separator）不代表本地组件已具有；本批不升级底座、不重装组件、不为补齐官网目录安装整套组件。共享布局自身提供必要间距/换行，Portal 不依赖页面后代选择器。

迁移边界：UI 布局与路由不需要 schema 变更。申请幂等、版本族一致性、报告来源及实际覆盖仅在对应业务增量确有持久需要时增加最小字段/唯一约束，由集成人单写必要数据库迁移；先核实存量，不能补造历史。数据库迁移是用户明确允许的类别，不延伸成旧配置迁移、应用兼容层或双轨接口。不得改写已落下的人工要点迁移；新调用方全部使用当前合同，不保留无键或缺字段 fallback。保留有事实依据的权限、财务、审批及归档守卫，不把 pending、预检或串行按钮当并发保证。

本节保留第一批纯契约实现的历史范围；后续 W05/W06/W07 的持久层和原工作台接线已在本轮增加，现行边界见 §6.4.1，实际证据见计划 §8.4。

W01.2/W04.1 首批在 `src/lib/workbench/` 建立不依赖 Prisma/Next 请求上下文的 Zod 契约：运行模式与操作者描述、三类来源版本、真实定位、解析覆盖、索引代次/指纹、明确结果及错误。材料继续使用具体 `Document.id + sha256`，不增加平行版本表；法源核实/正文权益、经验审核/撤回独立于来源类型。

`src/server/rag/` 的共用检索边界只接受可信服务构造的范围。适配器只取得具体绑定清单；空范围不调用后端，返回内容必须重新对应当前授权、原件版本、有效代次和已处理范围。当前范围与稳定锚点由服务回调读取，后续 W05/W06 再接真实持久层；这批可验证纯校验与异步撤权反例，不声明现有页面已具备该保护。失败、不支持、未完成、待核对与成功无命中分开，未经核对的片段不进入界面或生成模型。

**历史引用与新结果分开**：新检索/发布核对有效索引代次；打开历史引用核对当前读取资格、原件 ID/hash、真实锚点及其内容，不强求旧锚点等于当前索引代次。索引重建不能使历史成果改指新版本，也不能成为撤权后继续读取的理由。

两类工作包由测试源码生成合成 UTF-8 字节、实际 hash 和可定位文字，并给出独立的支持/反证/矛盾/未知预期。生成原件及原始运行输出留在隔离验收环境，不进入默认 seed；测试生成器与断言随代码审阅。部分覆盖是明确构造的输入样例，不冒充真实 OCR/表格解析。专业标注、实际后端、Windows 和界面验收按对应任务接续。

- 用户纠正后，个人启动器必须启动根应用的生产 standalone，复用 `src/app` 与 AppShell，而非独立材料原型页面。统一服务端操作者解析覆盖页面、动作、下载/预览/导出；客户端通过统一 actor context 读取，Personal 不挂 NextAuth SessionProvider、不发起登录会话轮询。Server 继续使用原有认证。模式由启动配置决定，不能由请求切换。

- 主应用工作区使用 Prisma 默认 CUID 创建真实 User，manifest/数据库版本为 2；不重写旧工程原型 UUID 或历史外键。文件密钥首次产生后持久化，缺失时拒绝启动，不生成替代密钥。原件使用工作区私有存储；生产 Personal 缓存唯一 PrismaClient，初始化 seed 不创建管理员，只给稳定操作者建立基础字典和模板。
- 本地入口用短生命周期随机通道值设置 HttpOnly/SameSite=Strict cookie 后跳回干净根地址；它不决定模式、操作者或业务授权。逐次复核 manifest、数据库元数据及有效操作者；写操作校验精确 Origin/Host。日历/桌面文件入口保留其专用令牌并加本机边界。账号/TOTP/组织管理在路由与动作两层禁用，业务配置按明确白名单开放。
- Personal 的财务、审批与归档采用显式本人能力并核对真实对象归属，不授予 ALL/管理员/财务岗位。登记保持待确认，发票确认和实际开具分开，法定代表人章与归档快照条件保留；事务 helper 复用传入连接，审计记录真实单人决定。当前 M1 关闭调度（`DISABLE_CRON=1`），原定 W17.3 调度生命周期工作现已搁置。
- 原始字节的 SHA-256 是来源校验依据；解析分别记录 PDF 页、DOCX 不可变抽取文本偏移（尚非原文件段落映射）、表格单元格/区域和图片位置。空文本扫描页、公式无缓存和失败页不变成已处理；OCR 使用显式 provider，原件不被改写。
- LanceDB 固定 0.41.0，M1 隔离工具运行时 Node >=22；词法使用 ICU，词法/向量两路均先按可信 binding/代次过滤，再合并。重新写入须验证来源、维度和配置指纹；索引不是引用原件仓库。
- RAGFlow v1.0.0 的 HTTP 适配以固定 Go 实现为准：生命周期请求与观察到的终态分开。上传响应丢失进入待核对；取消、删除未观察到结果不记完成。远端 xxh3-128 内容摘要不能代替本地 SHA-256。`prepare-ragflow.mjs` 固定上游提交、文件校验与镜像摘要，输出仍为 `PREPARED_NOT_DEPLOYED`，没有证明容器启动、健康、解析或持久化。
- 独立模型与 RAGFlow 服务分别配置凭据。公网沿用安全出站校验，受信本机/内网地址由进程启动配置精确允许，禁止重定向扩大范围；原始服务错误不写入用户输出或日志。模拟 HTTP 服务只证明协议与失败处理，不计真实模型/RAGFlow 验收。

### 6.7 专业工具所需的共用边界（研究决定，待实施）

来源及采用取舍见[研究 §3.5](RESEARCH_AND_DECISIONS.md#35-按国际执业能力审查参考实现2026-11-16)，任务和场景见计划 §3.9—3.10。下列只细化 W05—W12/W14/W15，保留 M1 历史状态，按当前 Server 唯一交付、Personal 搁置和第三方可选策略实施；具体表/迁移在相应任务按最小增量确定；涉及自动候选、模型供给、嵌入/重排或 RAGFlow 的条件仅对实际启用分支生效，不阻断人工业务。

1. **摄入身份不等于文件内容身份。**批次、单件操作意图、来件来源与具体 Document 版本分别可追溯。操作幂等键用于重复请求；SHA-256 用于内容核对，不成为跨事项身份或权限。不同收件时间/提交方即使同内容也保留业务来源；同文件名不推断新版本。派生复用须内容、解析/OCR、语言/配置和必要嵌入指纹匹配，且不泄漏另一事项的命中或缓存内容。
2. **候选裁决与来源生命周期分别存。**候选身份使用事项、类型及明确业务识别字段，不能只用标题、日期或向量相似度。每份来源保留材料/解析版本、原文和提取内容；人工接受/拒绝/纠错/重新打开保留历史。重跑不抹掉处理结果，仅明确业务身份及实质信息均相同的来源可关联既有候选/事实，语义相似只形成合并建议；实质变化、新反证、身份修正形成待复核，允许拆分。事务内核对当前状态/目标版本/唯一操作；候选接受不触发财务到账或其他独立批准。
3. **AiRun 记录处理范围、供给范围与引用用途。**保存任务目的、计划材料清单、解析覆盖、召回锚点、最终每次模型输入范围及被排除原因，引用另记到论断的用途；“供给模型”不声称已被模型理解。定向问答可用检索，指定材料审查按页段推进，未读单元不伪装无问题。逐字匹配要处理重复文本和未知定位，语义支持由复核处理；原文/敏感运行内容保存在受控业务存储，普通日志只记标识、统计和错误码。
4. **研究记录在检索之上。**沿既有三类来源合同记录研究问题、用途、受众、时限/成本约束、法域/相关日期、查询及来源版本。检索/排序/重排只是找材料；来源身份核实、相关时间有效性、例外与不利依据、与事实的适用分析分别记录。无结果、未取得、解析失败、未供给模型、来源不可核实不能合成一个空值。跨文档问题表后续按问题集与材料版本固定，每格记录有依据结论、已读未发现、未读/失败或不适用及其理由。
5. **模板准备采用轻量核对。**复用实际变量、缺项、本次值和快照；少量明确条件限于本期模板，换模板/主体/程序重新展示需核对字段。只读准备、临时渲染及主数据编辑分开，W10.2 处理 buildContext/applyOverrides 已证实副作用。通用访谈、递归跨会话依赖和 AI 补问暂缓，不引入任意脚本或表达式运行。
6. **复核问题及来源影响归领域层。**问题绑定具体文书/位置/依据，回应、修订、处理与文书批准分开。M3 只沿实际 Document/SourceAnchor/研究等直接关系提示影响，范围缺失如实报告；知识与旧成果间接多跳不自动排入 M5。历史批准与交付版本不更新；Word 往返比较仍是后续只读分析。
7. **技术运行和律师责任分别恢复。**AiRun 仅增加少量固定步骤/运行版本/失败记录/等待标识，JobQueue 仍负责租约、重试与可靠投递；恢复核对 run/step/等待实例和当前权限，重复回调/迟到结果不能推进新一轮。Task/WorkResponsibility 负责外部等待、内部责任和复查日期。主动取消的外发不自动续做，意外中断按既有授权/批次策略恢复；远端结果不明先核对，删除补偿可继续。领域事件携对象 ID/版本/操作 ID，不把正文广播为通用事件。
8. **客户决定、费用与交付保持各自权威。**客户目标/预算是有来源和确认状态的约束；指示变更不自动修改 Engagement、收费或财务确认。聚合活动读取现有对象并逐来源鉴权、稳定分页，计数不暴露无权对象。交付清单绑定实际成果/附件版本、未决项及受众；服务端逐件核对交付资格，沿既有文书/归档服务提交，不因摘要可见而放开附件。
9. **恢复有可核对的产物。**在既定一致恢复点协议上保存 manifest 和只读完整性结果，区分原件/业务/必要配置与可重建派生数据。核对缺失/内容不符、旧引用、远端绑定及授权待核实项；孤立文件先报告和隔离，不自动删。manifest 保存密钥标识及恢复所需关系，不泄露密钥值；索引重建读取固定原件，RAGFlow 内置解析记录 parser_id、parser_config 与上游版本，自定义 Pipeline 才额外记录/核对 pipeline_version_id；内置模式的该字段记不适用，不能制造配置缺失。同版恢复与跨版升级分别留证。

以上共用 TypeScript 领域与契约；Personal 由稳定本机操作者和本人确认驱动，Server 使用真实会话、作用域及审批资格。RAGFlow、LanceDB、模型提供商不能决定客户授权、法律结论或批准。当前 Server 把新动作接入现有事项/材料/文书/客户页面，UI 改版仍后置。AppFlowy 仅印证模块/平台边界，无新增语言或同步方案。

后续企业治理与多法域能力先按目标使用方式设计。SSO/明确的事项隔离墙/企业审计与数据区域，不由通用 RBAC、RAGFlow Team 或多语言界面推导；建立反例和支持范围后再决定适配，不改变 Personal 无认证，也不以这些未来能力阻断当前首发。

| 实际交付 | 最小 DeliveryRecord 在“核对并保存清单”时创建：固定具体 Document 明细、顺序、接收对象/实际联络快照、披露范围与准备人，实际发送时间仍为空；首次导出前已持久化。导出事件、发送登记、回执/回复分开。清单固定后改文件/接收范围另建准备记录并关联原记录，不覆盖已导出清单；实际发送登记追加时间/渠道/凭据或明确事实说明 | 不复用技术通知投递表，不以 isLatest 重建历史包；发送记录不自动修改客户决定、文书批准或归档 |

表中研究、问题、交付等是当前具有独立业务历史的必要记录；不为只读列表另造快照表。稿件内容、实际交付等需要固定历史的记录可以保存当时值，不把“不做非必要投影”误解为丢掉业务证据。具体 schema/索引在对应切片由集成人单写；变更后的现行入口一次更新，不保留缺字段/旧对象形状 fallback。数据库升级只能按核实过的数据处理，已执行迁移不改字节。

W09.3 的知识候选/审核/发布/撤回表、B 比较矩阵、E 规则/日历/计算历史及待复核差异模型、F 自动简报和 C 通用访谈/递归跨会话依赖均不在本期持久化设计内。保留原数据与现有守卫，不为这些暂缓方向预建 SQL、服务、权限或 UI。未来若重启知识发布，仍须先确定候选私有范围、脱敏审核、真实受众与各读取入口的撤回规则；现有 FirmFile 的资料和模板管理继续按原规则。

#### 权限、版本与写入

- 研究/方案入口沿现有事项读取/主办协办管理边界；读取正文、引用、历史和导出继续逐来源核资格。生成或修改 Document 继续使用既有 documents.write 及事项守卫。费用字段使用原财务裁剪；隐藏按钮不能代替服务端校验。
- 人工复核按动作授权：提出问题可由有目标文书读取权的本事项办理人员，或当前具体 Document 的合格 DOCUMENT_APPROVE 人员执行；作者回应、关联修订及改正文仍需原办理/文书写入资格，记录真实人。核对处理沿该文书现行复核/审批资格及本人例外，问题处理不执行批准。原 /approvals 直达同一 Document/问题面板，不绕经无权访问的事项页。
- 普通研究、分析/简报、OPTION/DECISION 及其历史、MatterBrief/客户聚合按实际来源复核当前资格；含不可读来源的派生正文不从缓存继续输出，允许获准的占位及补救。现有单来源 sourceView 或普通 visibility 不足以授权新增研究/费用关系；不靠段落猜测删改正文，不做全文污点或跨案多跳。
- **具体审批附件的明确授权单独处理：**沿 `canReadDocument` 已有、真实绑定该附件的当前审批资格或合法审批历史，开放该具体版本正文；不要求审批人同时成为整案经办。只限这个既有审批授权分支，普通案件读取/下载权不能据此跳过派生来源核验，也不能在来源校验失败后改走此分支。底层研究、原件、引用片段、问题中的额外来源、费用接口、客户历史及导出/交付各核自己的资格；无权只显示受限占位，不下发摘要/片段，不能登记为原文已核实。送审/出稿仍核发起人的实际来源和披露资格，不借送审传播未获准费用或材料。目标或实际来源撤回/作废、附件授权失效时，受影响的 M3 派生正文/导出继续阻断，缓存和历史不例外；C09 对 AI 报告的专门来源守卫不放松。不新建可配置授权豁免或复制资格快照。
- 正式交付清单保存和每次导出都按具体版本复核当前交付/披露权限及既有必要审批；需批准成果未获批准就阻断并定位原审核入口，普通来源附件不被一律追加审批，已批准历史稿不要求同族最新。清单保存不提供永久导出资格；发送登记只能说明实际发生事实，不能补造批准。原案已归档时沿既有许可处理，不能用交付登记通用放开写入。
- 实际交付后内容/明细/发生事实不覆盖；补发/更正追加关联，回执和客户确认追加，不回写已经发生的旧记录。
- 新增正式写入使用相应领域事务、当前有效操作者/权限/对象/状态和所见版本；如确有重试创建风险，复用现有稳定请求键及唯一约束模式。服务器在一个负责边界归一并计算必要请求指纹，UI/包装层不重复计算。审计与业务变更一致提交；界面 pending 只防误触。
- D 的加边/解除/环检查及 COMPLETE/REOPEN/CANCEL 复用现有 `approvalTransaction` 的 Serializable 与事务锁；检查当前关系/责任、写入与审计在同一事务，不能在事务外通过后再写。单条、批量和责任面板共用此合同；先核资格再识别 DONE 重放，CANCELLED 不算完成，批量沿现有逐项结果、不自动重排。只删除本切片实际触达的旧直接写 completed 绕行，缺现行责任数据报错；不另建图锁框架或全仓清理 readiness。
- 直接影响只沿本期显式关系：来源版本/研究/目标指示→所选方案/草稿/简报。新来源可提示已用旧版和待核对，不自动改结论、指示、批准或历史交付。没有关系只说明未检查，不做全案/跨案多跳完整性保证。

#### W11 当前实现合同（2026-11-16）

- `TaskDependency` 只存同案前置边与真实创建人/时间，复合主键阻止重复边，CHECK 拒绝自身；同案、环与所见责任 revision 在既有 Serializable 事务中核对。与办结共用该事务锁，只有责任 `DONE` 满足，`CANCELLED` 保持阻塞；解除需原因。
- `TaskWaiting` 是 Task 的追加子记录，一次新登记持有一个 UUID，失败重试保留。`initialCheckAt` 固定原请求，`nextCheckAt` 可说明原因后调整；重放先核当前资格，再比对同一 Task、发起人及原载荷，不把改期或已结束记录恢复成初始值。一个 Task 只允许一条未结束等待，部分唯一索引和结束字段 CHECK 保证写入一致。
- 登记、改检查日、结束等待和依赖变更都递增同一个 `WorkResponsibility.revision`。保存失败保留输入；刷新后责任 revision 已变化，界面展示现状并要求明确核对后才重提，不自动覆盖并发结果。
- 未结束等待阻止直接办结；结束等待必须记录实际结果或结束原因，不自动办结 Task。取消 Task 在同一事务结束等待并记录“任务取消：原因”，重开不会复活旧等待。等待结束文案为“已结束”，不推断已收到外部答复。
- 案件工作区只消费 `workPane=materials/facts/tasks/records`，任务以 `task=<具体 ID>` 保存和重开；不读取旧 `work/scope`。全案任务不从 `stage.tasks` 拼接，原保全环节创建也返回真实 ID 并刷新同一列表。案件 URL 传预期 matterId，真实 Task 不属于该案时明确拒绝；其他责任入口仍解析实际 Task 再鉴权。
- 读取保持现行事项业务读取资格，团队概况授权不开放任务正文。写入仍需当前经办关系、`schedule.write` 和允许状态；读取资格不能变成管理资格。任务详情、等待和同案依赖复用原对象；不加平行状态或图调度平台。

#### 模板、期限和可选能力的确定边界

1. `buildContext` 改为纯读取及本次内存渲染组装；删除其隐式 `applyOverrides` 主数据写入。模板选中的 Client/Party/程序以确切 ID 解析，不按“第一个对方”代替用户选定主体；需要改主数据使用原编辑动作及权限。保存 Document 继续消费 C05/C06 的现行版本/事务合同，RP05 与 W10 同一文件先交接再写。
2. 条件字段只服务本期实际模板：复用变量/缺项/本次渲染快照，少量明确条件直接按已审模板判断。切模板/主体/程序重取实际字段并人工重核，失效临时值不静默复用；不实现任意表达式、通用自适应访谈或跨会话递归依赖。现有 docxtemplater/PizZip/docx 和表单库足够，不引入 Python/Groovy 服务。
3. 期限继续沿现有确定性规则、确认/人工调整及 recalc-guard，保留当前来源与理由。W11 已修正已证实的异常吞没和读取 15 日却扫描 30 日的问题：查询故障中止规则期限写入；年度无录入给出未核对状态而不生成建议日期；年度有录入不等于全年完整。Holiday 用上海日键、完整业务日查询和固定上海正午新增；已有同日安排保留原 timestamp，不猜原部署时区。纯日期算术用 UTC；`computeDeadlineDate` 保留现有明确 civil 日期载体合同，不能仅因局部 `getDate()` 就认定其使用错误时区。E 完整计算历史、规则/日历版本及逐条差异复核暂缓，不新增相应模型；任务安排不改法定日。
4. 普通人工流程是明确产品路径，不是外部失败 fallback。启用的服务按用户选择调用；失败保留原稿和错误，不静默换 provider/模型/资料集，不扩大授权范围。NOT_SENT 离线诊断、C09 的真实 ReviewRecord 输入和未来 AiRun 各如实登记。
5. 无需为了 M3 人工链先建完整 AiRun/技能注册执行平台；实际增加自动技能时才按既有契约记录那次输入、工具、版本、覆盖、失败与人工采纳。外发授权/迟到撤权守卫必须从该自动切片起具备，不能先放开后补。

#### 文件与执行次序

研究→起草/人工复核→实际交付是首条成果链。交付 owner 可先用已有 Document 开工，不等整项 W11；研究 owner 关闭首条研究切片后转事项任务/等待/同案依赖，与文书/交付并行，最后在同一事项场景汇合。root 单写必要 schema/SQL、来源资格与主壳，仅接收 C02/C05/C06/C09/C10/C12 中本批消费的合同，不等待整包专项。

新增对象定位只补实际消费者：研究 ID/修订、具体 Document ID/问题 ID、固定交付清单 ID/回复关联。root 随切片更新现行路由与调用方，支持保存/刷新/审批入口/新增客户动态到同一对象，失效或失权明确返回，不静默换最新版；不改全部旧历史链接或建路由注册表。计划 §7.11.1 保留开工前基线；本轮已在主壳及消费者采用单一 `workPane` 合同，没有接入另一工作区的未合代码或保留双参数兼容。

W09.3/B/E/F 和 C 通用机制不分配 owner，不预建模型。迁移/权限/审批/实际派生关系改动只做必要真实 PG 与 Server 页面验证；实际执行分别记入计划第 8 节。

#### 本轮落地的存储与授权合同

两条新增迁移分别为 [研究/复核/交付](../prisma/migrations/20261117000000_m3_research_review_delivery/migration.sql) 与 [等待/同案依赖](../prisma/migrations/20261117010000_m3_task_waits_and_dependencies/migration.sql)。现有迁移字节保持；未增加知识发布、结构化比较、自动简报或期限重算平台。

- ResearchRevision 每次保存新修订，ResearchSource 和 DocumentResearchSource 固定具体输入；数据库禁止覆盖历史，仅允许首次核对字段的规定变化。ISSUE 输入使用 EvidenceItemRevision 的固定来源快照，不读当前争点补旧研究。
- DocumentReviewIssue 只维护当前问题状态/版本，RESPONSE/CHECK 事件追加；DeliveryRecord/Item 和各交付事件固定，首次 SENT 有唯一约束。TaskWaiting 单任务仅一个未结束等待，结束后保留；TaskDependency 在现有授权锁和事务内查同案/环并提交。完成入口只认责任 DONE。
- READ、EXPORT、SUBMIT 是同一来源守卫的明确目的。具体 DOCUMENT_APPROVAL 只在 READ 选用，不能被递归用于导出或再次派生；来源撤回、hash/事项不符或当前失权均停止相应内容发布。不同目的不存在失败后改用另一授权的回退。
- 新研究稿和模板稿创建时持久明确 familyId；人工简报及正常上传沿现有摄入事务。新详情/复核不推断缺失族关系，读取不写回数据；上传新版在权限验证后、写文件前拒绝缺族原件，提交事务也不猜测或补写版本关系。新稿保留实际研究输入和模板快照，但不继承批准。
- 模板预览/缺项补全不写 Client/Party。生成请求重放在最终写入和响应恢复时校验本次身份及已提交原件；不能因为响应丢失误删已提交文件。文书送审和入卷对内置岗位也使用真实事务，状态与审计一起提交。
- 归档沿原 ArchiveRecord.frozenManifest，在原批准事务固定选中成果的研究修订、人工问题/事件、完整交付清单/事件。额外来源、修订稿、凭据只进入引用核验，不扩增物理选件。导出只消费原冻结值，不以当前数据补造缺失清单；已有旧冻结值不事后加入新历史。
- 完整包在文件 I/O 前后和归档响应释放前核当前账号、岗位、关联、独立财务/归档权、每份材料及冻结来源。选件原件按已有校验读取一次；在办包同次读取后核 hash/大小，失败停止整个包，不写缺件占位文件。日常详情不重新扫描原件。

这些实现使用现有 Prisma、Zod、文书生成/存储、审批和责任服务，以及 shadcn/Radix 组件，没有新增依赖。真实 PG、组件、页面、部署四层证据不互相替代；生产迁移、发行镜像和整套恢复仍按 M4 执行。

## 11. 当前源码的开发、部署与恢复

本节归并原安装、云开发、二开接续及运维说明，适用于当前已有的 Server 源码。当前 Server 固定发行仍按 W13 实施；RAGFlow 单独可选，Personal 搁置，本节命令不代替发行/恢复验收。当前脚本与配置以 [package.json](../package.json)、[环境模板](../.env.example)、[Dockerfile](../Dockerfile)、[Compose](../docker-compose.yml) 为准。

### 11.1 环境、初始化与凭据

使用 Node.js 22.19 或更高版本、npm、PostgreSQL 16；当前 CI/容器使用 Node.js 22。源码命令适用于 Linux、macOS 或 WSL。首次在独立开发环境安装依赖，并且仅在尚无私有 `.env` 时由模板创建；已有实例保留其连接、密钥和存储目录。

| 配置 | 要求 |
| --- | --- |
| `LEXORDER_RUNTIME_MODE` | Server 启动配置使用 `SERVER`；请求、cookie 或界面不能改变运行模式 |
| `DATABASE_URL` | 指向本次明确使用的库。Compose 的宿主访问 URL 与 `POSTGRES_DB/USER/PASSWORD/PORT` 对应；容器内部使用 `db:5432` |
| `NEXTAUTH_URL` / `NEXTAUTH_SECRET` | URL 对应实际 Server 入口；secret 独立随机生成，生产经 HTTPS 入口使用 |
| `STORAGE_ENCRYPTION_KEY` | 独立随机的 32 字节 base64 密钥；已有数据必须沿用原值，不能随部署重新生成 |
| `APP_STORAGE_DIR` | 应用、备份和恢复使用同一实际持久目录；不要只持久化数据库 |
| `SEED_ADMIN_EMAIL/NAME/PASSWORD` | 仅用于 Server 首次管理员初始化；自行设置强密码，不能使用模板或 seed 中的演示默认值 |

两个密钥分别生成，例如各运行一次 `openssl rand -base64 32`，存入私有配置并独立保管。云开发运行器要求数据库密码与首次管理员密码至少 16 个字符。

全新独立 PostgreSQL 环境的顺序见[根 README 源码运行](../README.md#源码运行)：`npm ci` → `npm run prisma:generate` → `npx prisma migrate deploy` → `npx prisma db seed` → `npm run dev`。数据库容器需先启动并就绪。首次 seed 只建立管理员、字典、规则、配置和内置模板；不写入演示案件。已有管理员不会因重跑 seed 自动改密码，已有实例更新用第 11.4 节。

上述账号初始化只属于现有 Server；Personal 的首次打开只建立/选择工作区、稳定本机操作者及空业务数据，不沿用 Server 账号/岗位初始化。

### 11.2 无 Docker 的云开发与隔离验收

[开发运行器](../tools/cloud-dev/run.mjs) 在 `.runtime/cloud/pgdata` 管理独立 PostgreSQL，依赖单独锁定于 `tools/cloud-dev`。它固定 `SERVER` 并显式拒绝非 Server 模式；使用私有 `.env` 中的 loopback 数据库地址，要求显式端口、库名和强密码，只新建不存在的开发/验收库，已有目录继续复用。根 `npm run dev` 仍是开发预览入口，不代替生产构建与 HTTP 验收。

```bash
npm ci
npm ci --prefix tools/cloud-dev
npm run prisma:generate
npm run build
node tools/cloud-dev/run.mjs serve
```

`serve` 执行开发库迁移与基础 seed，再启动 `.next-build` 生产构建；停止时在拥有该进程的会话使用正常终止信号。出现 `postmaster.pid` 时先确认并正常停止原进程，不删除锁文件强行复用数据目录。不同执行会话不一定共享 loopback 网络，应用与其数据库应由同一运行器管理。

| 模式 | 用途与隔离范围 |
| --- | --- |
| `serve` | 启动当前源码开发页面，仍使用 Server 登录；不会形成个人安装包 |
| `test` | 对 `<开发库名>_acceptance_test` 执行迁移、结构核对及测试，不在开发库执行测试清理 |
| `verify` | 在同一独立验收库执行测试、seed、生产服务及 HTTP 核查；可用 `WORKBENCH_QA_SCRIPT` 指向受审阅的绝对脚本路径 |

验收另用运行目录内的 `acceptance-storage` 和独立 `acceptance-storage.key`，与开发原件、密钥分离。运行器默认关闭 cron 和自动备份，内置 PG 包不自带 `pg_dump`；开发就绪不表示备份、独立 worker 或完整浏览器流程已通过。

托管预览仅在环境明确提供 `sites-preview` 与 `SITES_MANAGED_LINUX_CONTAINER=1` 时使用 [preview-server.mjs](../tools/cloud-dev/preview-server.mjs)，由预览管理器传入端口与入口地址，并使用独立的 `.runtime/managed-preview`。旧会话地址不是永久发布地址；预览停止使用管理器的生命周期，临时运行环境不承担生产数据保管。

### 11.3 部署、调度与可选服务

根 Compose 的 `full` profile 提供已有 Web 应用与 PostgreSQL，尚未包含 RAGFlow。M1 的 `tools/workbench-m1/prepare-ragflow.mjs` 已提供固定来源和镜像的配套准备入口，但状态为 `PREPARED_NOT_DEPLOYED`；当前无 Docker/Podman，未验证该配置的实际部署。现有业务镜像包含脚本所需源码、`tsx`、Bash、PostgreSQL 客户端和 Next 配置，不沿用旧指南临时挂载源码才能 seed 的假设。

本轮真实服务检查使用 `npm run verify:services --prefix tools/workbench-m1 -- --mode=server`，只检查 Server 生成 API 与 RAGFlow 合成材料链；默认 `all` 仅保留兼容，本轮不运行。当前两项均为 `NOT_CONFIGURED`、退出码 2，表示缺真实服务/模型配置，不是联调成功。RAGFlow 服务凭据与其嵌入模型配置、LexOrder 生成模型凭据分别提供，不能互相替代。

容器首次安装依次完成：构建 app 镜像、启动并等待数据库就绪、在一次性 app 容器运行 `npx prisma migrate deploy`、明确传入私有 `SEED_ADMIN_*` 后运行 `npx prisma db seed`、再启动正式 app。当前 Compose 没有转发 `SEED_ADMIN_*`，仅修改宿主 `.env` 不会自动注入；使用明确的私有 Compose override 或等效注入配置，不把初始密码写入仓库。已有实例不重复初始化管理员。

部署时核对实际转发的环境变量、持久卷及网络入口；默认端口映射不自动提供 HTTPS 或网络隔离。`dev` profile 的 Mailpit 仅为开发收件箱。不得把 Compose 中的历史容器名或包版本号当成新的 LexOrder 正式 release。

| 运行方式 | 调度约定 |
| --- | --- |
| `npm run start:with-cron` | 监督器启动 Web 与一个独立 worker；Web 设置 `DISABLE_CRON=1`，worker 单独启用调度，任一子进程退出时终止另一进程 |
| 分别管理 Web 与 `npm run cron:worker` | Web 显式关闭进程内 cron，worker 只运行一个实例；由进程管理器负责重启和退出 |
| 单独 `npm start` | 沿用已有进程内调度；不能同时再启动独立 worker |

监督器默认监听 `127.0.0.1:3000`，按部署设置 `LEXORDER_HOST/PORT`。数据库迁移由安装/更新流程执行，启动命令不代办。已有启动补扫覆盖最近 15 分钟漏跑的部分任务，周报按用户/周去重；不等于完整休眠恢复、跨实例去重或备份补跑。worker 关闭等待与监督器终止期限也不保证长备份必然完成。具体入口见 [run-with-cron.mjs](../scripts/run-with-cron.mjs)、[standalone.ts](../src/server/cron/standalone.ts)。

| 可选能力 | 配置与当前边界 |
| --- | --- |
| cncases 外部案例服务 | `CNCASES_BASE_URL` 为服务根地址，不含路径前缀、用户信息、查询或 fragment；浏览器跳转可另配 `CNCASES_PUBLIC_URL`，未配置时不泄漏内部地址。默认拒绝私网端点，仅受信本机/内网服务显式启用 `CNCASES_ALLOW_PRIVATE=true` |

| RAGFlow | HTTP 适配与固定准备脚本保留，但尚未接当前工作台的持久配置消费链；设置页明确标注待接入/未验证。无运行实例或账号不影响内置处理/搜索及业务 |
| 传票首页解析 | PDF 先提取第一页文本；图片/扫描可选 Tesseract 的 `chi_sim+eng`，扫描 PDF 另需 `pdftoppm`。可配 `SUMMONS_TESSERACT_BIN` / `SUMMONS_PDFTOPPM_BIN`；当前默认镜像未安装这些 OCR 工具 |

cncases 保留服务端授权、超时、2 MiB 响应上限、禁重定向与同源链接检查，不内置裁判文书语料。传票识别仍仅处理首页；后备视觉 API 接收首页图像，缺时间不补造默认开庭时刻，也不把出具日期当开庭日期。外部服务失败、未配置和无结果分别呈现。这些模块不等于通用 OCR 或已接通可选 RAGFlow；未启用相关服务不阻断内置业务。

### 11.4 更新与旧版本边界

已有、迁移链明确的 LexOrder 实例先保留可恢复副本，停止对应写入和 worker，在目标代码版本执行：

```bash
npm ci
npm run prisma:generate
npx prisma migrate deploy
npm run templates:sync
npm run build
```

然后按既有进程管理方式启动，检查健康、实际登录和受影响业务。`templates:sync` 同步已有基础/执行模板；不是迁移数据的替代步骤。容器采用相应的新镜像和一次性迁移/模板同步任务；不得为了追赶 schema 使用 `db push`、reset 或删除现有迁移记录。

历史 LawLink 1.3.x 的基线转换有特定起始状态、增量 SQL 和 migration resolve 顺序，仅按[固定历史升级指南](https://github.com/zaenzhang/LexOrder/blob/690232270b46e1f1b105df11bdff167fe7afb80d/docs/RELEASE-GUIDE-v1.3.md)与 [prisma/upgrade](../prisma/upgrade/v1_3_x_to_v1_4_0.sql)识别适用范围，在副本演练；它不是任意旧版本到当前 LexOrder 的通用升级命令，也不代表本轮已验证升级。PostgreSQL 大版本升级另遵循第 10 节 [P1]。

旧财务试迁移与切换准备脚本属于历史演练工具，不进入安装/升级步骤。原 `docs/` SQL 与[归档迁移](../prisma/migrations-archive-20260921/20260919000002_business_workflow_repair/migration.sql)内容完全相同，两个脚本复用归档文件；模型 hash 与目标库预检保持原样。切换准备产物写入忽略提交的 `.runtime/workflow-cutover-20260919`；不将归档 SQL 放回当前迁移链，也不通过修改历史 schema 绕过预检。

### 11.5 备份、恢复与密钥

[备份任务](../src/server/cron/jobs/backup-database.ts)和 `npm run backup:now` 调用 [scripts/backup.sh](../scripts/backup.sh)，生成 PostgreSQL custom dump、存在的本地原件目录归档和 manifest。运行需要 Bash、与服务端兼容的 `pg_dump`、可写持久目录；`BACKUP_DIR` 和 `BACKUP_KEEP` 管理输出和保留数量。手动命令是显式备份请求，不受 `BACKUP_CRON_ENABLED=false` 的自动任务开关限制。

`BACKUP_PASSPHRASE` 可加密备份产物，未配置时产生未整体加密的备份；它与文件主密钥用途不同。脚本不自动打包 `STORAGE_ENCRYPTION_KEY`、完整私有配置或 S3 对象，需独立保存原密钥、必要配置和实际对象存储副本。Compose 的 `backups` 命名卷仍与主机同在，不能当作异地副本；原件目录缺失时脚本会跳过，不能仅凭退出成功判定备份完整。

恢复时以隔离实例核对版本、目标库、备份 manifest、原件路径及密钥，先验证数据/权限，再开放业务和检索。数据库和文件需要同一一致性时点，备份期间应停止相关写入或使用已验证的一致性方案。已有新写入后的回退另行处理数据，不能直接覆盖旧备份抹去新增事实。

当前 [restore.sh](../scripts/restore.sh) 仍使用旧 `STORAGE_PATH` 变量、只直接读取未加密的 dump/tar 文件，并会跳过缺失文件；使用前须核对实际 `APP_STORAGE_DIR` 与归档结构、处理解密，并在隔离目标验证。它尚不能作为完整的一键恢复保证。本轮只保留并核对说明，成功备份/恢复、对象存储恢复及将来的 RAGFlow 状态恢复仍需 W13 验收，不能用备份失败路径测试代替。

`STORAGE_ENCRYPTION_KEY` 同时关系到附件、证件号密文与盲索引；只换环境变量或派生域会破坏现有数据读取/检索。当前没有已完成的自动密钥轮换工具，轮换需要明确的旧数据解密/重加密、盲索引重建、恢复副本与一致性验证方案。实际启用向量检索或 RAGFlow 时，恢复还须核对文档版本、解析/嵌入指纹、索引代次和服务端绑定；先恢复当前授权，索引按固定配置重建。
