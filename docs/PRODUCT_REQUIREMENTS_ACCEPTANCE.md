# LexOrder 产品需求与验收基线

更新日期：2026-11-16。状态：需求与验收设计，未实施的条目不能作为产品能力声明。

本文依据用户本轮补充的律师工作台需求整理；工程路线见 [重构方案](REFACTOR_DESKTOP_TEAM_RAG.md)，执行任务见 [实施计划](WORKBENCH_PLAN.md)。招聘研究用于补充技能设计，不替代本文件的产品目标。后续实现应同时引用需求编号、技能编号与验收结果。

## 1. 产品核心与首发范围

**以法律事项为中心，帮助律师完成可追溯、可复核、可交付的专业工作。**

三个产品承诺：

1. **迅速恢复上下文**：客户目标、当前状态、关键事实、风险、最近决定、等待事项和下一步清楚可查。
2. **重要结论有可核查的依据**：区分客户陈述、材料记载、律师推断、法律依据及待核实事项，保留来源、版本与反向证据。
3. **承诺有责任人和结果**：任务、法定期限、客户决定、内部复核、实际交付和费用记录相互关联。

首发聚焦中国大陆个人律师和小团队的民商事诉讼、仲裁。合同审查、常年顾问、交易与专项咨询继续复用 Matter；保留既有能力，不因首发重点而删除已有业务类型。此处“法律事项”是产品概念，沿用现有 Matter 主键、路由与关联，不为改名迁移整套数据。

每个正式 release 至少提供**最小化个人运行版 Personal**与**服务部署版 Server**两个可选产物，共用业务核心。个人安装后独立使用本地工作区，无需手工维护 Node、数据库、Docker 或 RAGFlow；部署版可自行部署或代管独立实例，普通成员使用浏览器。远程访问客户端不能计作个人独立版。完整离线、个人独立和团队协作分别验收，详见[双版本发布与资源预算](RELEASE_VARIANTS_AND_RESOURCE_BUDGET.md)。

## 2. 首条完整工作流程

**目标与客户指示 → 材料入库 → 事实与争点 → 带来源草稿 → 律师确认 → 行动与客户跟进 → 实际交付 → 归档与复用。**

每一步保留与前一步的关联。一次问答成功、文书生成成功或安装器启动成功，均不能单独代表该流程完成。

| 工作环节 | 首发必须产出的结果 |
| --- | --- |
| 理解委托 | 目标、范围、约束、客户指示及其来源；复用冲突检查与收案门禁 |
| 重建事实 | 时间线、五类证据要点、多来源、支持与反向材料、缺失材料 |
| 判断与策略 | 争点表、法律研究记录、候选方案、风险与成本、选择理由和待客户决定项 |
| 执行 | 经复核的文书版本、任务、程序事件、期限、责任人和依赖 |
| 沟通 | 已完成、等待、下一步、待客户决定和费用变化的进度简报 |
| 交付与结项 | 实际交付版本、对象、时间、渠道和证据；客户确认单独记录；保留财务及归档规则 |

## 4. 三类 RAG 的业务边界

| 范围 | 回答的问题 | 必备元数据与控制 |
| --- | --- | --- |
| 当前事项材料 | 发生了什么、谁说了什么、依据在哪里 | Matter、具体 Document 版本、锚点、解析覆盖、材料/AI 权限 |
| 获授权法律资料 | 适用哪些规则和裁判、相关时间采用哪个版本 | 法域、机构、资料类型、效力角色、相关日期、有效期间、查询日期、原始 ID/链接、实际权益 |
| 个人/律所经验 | 类似工作怎样处理、可用什么方法和模板 | 原始来源、脱敏/审核状态、适用条件、受众、修订和复审日期 |

三类资料可共用技术管线，但每次回答保留来源性质。技能不得把“客户陈述”“历史经验”和“法律依据”混成同一种事实。无外部法库账号时，可在获授权范围内使用用户提供的法律材料验证流程，但不能将这项验证写成商业法库接通。

## 5. 最小增量设计原则

- **MatterBrief 为聚合视图**：从当前授权范围内的目标、决定、风险、任务和交付记录计算，不另存一套案件状态与负责人。
- **目标、指示与决定是业务记录**：利用现有范围/描述字段，补版本化指示和方案决定；保存来源、作者、确认人、时间和替代关系。聊天摘要不直接成为客户授权。
- **Document 即版本身份**：沿用每行一个版本，不新造平行 DocumentVersion 系统；索引与引用依附当前 Document 身份。
- **EvidenceItem 为证据要点主对象**：增多来源和要点之间的支持/反驳关系；技术实现不要求图数据库。
- **Task/WorkResponsibility 继续负责行动**：扩等待与依赖；等待不暂停法定期限，外部等待对象不替代内部负责人。
- **复核沿用现有审批**：AI 建议经结构化输出、校验、律师确认后调用既有服务；不新造绕过权限的通用写入通道。
- **DeliveryRecord 连接审核与实际交付**：绑定确切成果版本，人工登记交付证据；下载、发送和客户确认分别记录。
- **技能是有版本的工作规格**：工具、模型与提示词可以替换；执业资格、最终判断与客户授权由人承担。

## 6. 完整场景验收包

M0 准备至少两类合成或明确获授权的民商事工作包；优先包含合同、交付凭证、聊天记录、付款流水、法院/仲裁来件、一个反向材料和一个材料新版本。测试资料、实际客户材料和模型原始输出不提交公开仓库。

同一工作包在团队网页和个人安装版分别执行。个人版首次引导须明确配置业务角色、财务确认资格与审批路由；用一个真实用户走通既有规则允许的个人业务流程，保留确认动作和审计，不用虚拟第二审批人代替验收。系统管理员身份本身不授予这些业务资格；若现有审批规则无法满足该路径，先记录阻塞并审查规则，不静默绕过。

1. 记录客户目标、费用/时间约束及委托范围；沿用收案与冲突门禁。
2. 批量导入原件；出现扫描失败页、重复文件和长文时，覆盖状态可解释。
3. 形成事实时间线和争点表，逐条打开来源，列出反证和待补材料。
4. 研究一个争点，区分事项事实、法律资料与经验，保存适用日期和查询状态。
5. 比较方案并记录律师建议、客户决定及原因；客户改指示时保留旧版本。
6. 生成带来源分析草稿及一份模板文书；核对引用支持关系，执行真实审核路径。
7. 建立责任人、期限、依赖与等待；调整个人计划不改变法定期限。
8. 从真实记录生成客户进度简报，律师确认后导出；登记实际交付及回执。
9. 上传材料新版本，确认旧引用不漂移；过时分析和审核提示重新核对。
10. 完成既有收费、结项与归档流程；所用成果版本与交付记录可还原。
11. 在处理任务期间撤回一份材料，核查检索、模型外发、历史与引用边界。团队版另验证成员撤权；个人版验证本机工作区身份与材料撤回。
12. 在保存材料与投递任务的边界、解析/索引/生成阶段分别中断进程后恢复；证明任务不丢失。完成数据库、原件、必要密钥与配置的恢复演练，再重建索引。
13. 切换同维度但不同 provider/模型的嵌入配置，验证新代次构建、失败恢复和完成后的切换；不混用不兼容向量。
14. 从正式候选 release 分别下载 Personal 与 Server 产物：个人版在无开发工具、无团队服务的目标机验证基础与材料处理档资源；部署版从固定镜像/配置启动。两者完成同一 RAG、更新与恢复工作包，记录实际模型配置和外发/离线范围。

## 7. 如何判断产品有效

先记录同样工作包的人工基线，再测新流程；不预先宣称固定效率提升或 Rust/TS 性能倍数。

| 指标 | 观察方式 |
| --- | --- |
| 恢复上下文所需时间 | 间隔数日重新打开事项，找出目标、决定、风险和下一步 |
| 材料到时间线耗时 | 从导入开始，到律师核对后的时间线可用 |
| 事实与反证遗漏 | 对照律师标注的关键事实、矛盾、缺失材料清单 |
| 引用质量 | 分开检查“能否定位”“版本是否正确”“是否支持对应论断” |
| 草稿核查和返工 | 记录核对耗时、关键修改及不可采纳原因 |
| 推进连续性 | 等待项是否有内部负责人、下次检查时间和明确处理结果 |
| 交付质量 | 文书、证据目录、简报的返工；交付与客户确认是否可追溯 |
| 使用与恢复 | 用户能否自行安装、备份、恢复、更新；休眠后状态是否清楚 |

发布硬门槛：不得出现已知的越权披露、空授权放大、引用版本漂移、过时任务发布结果、未确认的正式写入或不可恢复的数据丢失。正式 release 须同时具备通过验收的个人与部署产物。个人资源首轮目标见专门预算，质量与材料规模在 M0/M1 冻结；未实测目标不能当成最低配置承诺，也不能用模型生成字数、聊天次数或菜单数量代替质量指标。

## 8. 首发后的扩展

持续使用阶段完善今日工作聚合、交接、知识审核、顾问周期及经营分析。更多法域、法库、司法接口和专业模板逐项建立规则、样本及访问条件。保留界面语言与法域分离，首发不宣称已经完成全球法律适配。

暂缓全面 Rust 重写、替换部署版 PostgreSQL、多检索后端同时实现、共享 SaaS、多端离线共同编辑、通用工作流引擎和完整客户门户。个人版为满足独立与资源要求所需的嵌入式存储/运行时适配，先经 M1 比较再实施，不一律延期。每项改变都说明它解决哪个已证实的需求瓶颈。
