## 1. 产品核心与首发范围

**以法律事项为中心，帮助律师完成可追溯、可复核、可交付的专业工作。**

三个产品承诺：

1. **迅速恢复上下文**：客户目标、当前状态、关键事实、风险、最近决定、等待事项和下一步清楚可查。
2. **重要结论有可核查的依据**：区分客户陈述、材料记载、律师推断、法律依据及待核实事项，保留来源、版本与反向证据。
3. **承诺有责任人和结果**：任务、法定期限、客户决定、内部复核、实际交付和费用记录相互关联。

首发聚焦中国大陆个人律师和小团队的民商事诉讼、仲裁。合同审查、常年顾问、交易与专项咨询继续复用 Matter；保留既有能力，不因首发重点而删除已有业务类型。此处“法律事项”是产品概念，沿用现有 Matter 主键、路由与关联，不为改名迁移整套数据。

**现行总策略（2026-11-16，按用户最后纠正）：当前唯一交付目标是 Server 部署版。Personal 直接搁置，不默认安排恢复，不作为开发、验收或发布门禁。RAGFlow、AI、OCR、嵌入/重排及第三方法库/MCP 全部按需配置；未配置、未授权或暂时不可用只影响对应能力，不阻止系统启动、登录和普通业务。默认先用内置材料处理与现有 PostgreSQL 正文检索。**

Server 管理员部署实例，成员通过浏览器使用；保留现有认证、角色与权限。RAGFlow 是可选检索服务，AI、OCR、嵌入/重排和法律数据库/MCP 是可选能力。服务未配置时提供普通事项、材料原件、手工记录/编辑/确认与已有成果；不能用空回答或伪造结果表示 AI 成功。性能仅观察。

**当前验收分工：** 仅执行 Server 受影响验证。Personal 和 Windows 不在当前范围，不登记为已通过，也不安排自动恢复；保留 LawLink 样式。若将来另行启动 Windows，开发侧只做逻辑/静态检查，实机由用户验收。

**当前范围裁剪（2026-11-16，用户决定及参考源码复核）：A 知识沉淀发布、B 结构化方案比较、E 期限计算/版本化重算深化、F 自动客户简报暂缓，优先级最低，不作为开发、验收、里程碑或 Server 发布门禁，也不自动排入 M5/M6。C 保留实际模板的字段补全、少量明确条件和人工核对，通用访谈/递归跨会话依赖及 AI 补问同样暂缓；D 有成熟参考，保留轻量同案任务依赖。案件内成果、既有方案/决定、资料/模板、期限/提醒和人工简报/实际交付继续复用。取舍及来源见[研究 §3.12](RESEARCH_AND_DECISIONS.md#312-范围裁剪与轻量采用的源码复核2026-11-16)。**

## 2. 首条完整工作流程

**目标与客户指示 → 材料入库 → 事实与争点 → 带来源草稿 → 律师确认 → 行动与客户跟进 → 实际交付 → 归档。**

每一步保留与前一步的关联。一次问答成功、文书生成成功或安装器启动成功，均不能单独代表该流程完成。

| 工作环节 | 首发必须产出的结果 |
| --- | --- |
| 理解委托 | 目标、范围、约束、客户指示及其来源；复用冲突检查与收案门禁 |
| 重建事实 | 时间线、五类证据要点、多来源、支持与反向材料、缺失材料 |
| 判断与策略 | 争点表、法律研究记录；用已有文本记录候选方案、风险与成本假设、选择理由和待客户决定项，不要求结构化比较矩阵 |
| 执行 | 经复核的文书版本、任务、程序事件、期限、责任人和依赖 |
| 沟通 | 已完成、等待、下一步、待客户决定和费用变化的进度简报 |
| 交付与结项 | 实际交付版本、对象、时间、渠道和证据；客户确认单独记录；保留财务及归档规则 |

| 能力 | 第一阶段最小产物 | 深度边界 |
| --- | --- | --- |
| SK01 上下文 | 目标/范围、最近指示/决定、风险、等待与下一步简报；客户页关联可见事项及既有跟进 | 复用现有对象；不另建完整 CRM 或第二套事项状态 |
| SK02 事实 | 可编辑时间线、多来源要点、支持/反向材料和缺口 | M2 的争点要点整理争议问题与材料；法律要件、证明责任及适用分析由 M3 的 SK03/SK04 接续 |

| SK05 方案与决定 | 使用已有 OPTION/DECISION 文本保存方案/建议、真实指示和来源/更正 | 结构化比较矩阵、自动差异、评分预测暂缓；未知不编造 |

| SK08 行动 | 内部负责人、轻量同案依赖、等待对象/检查日；现有期限/提醒及确认保护 | 成熟任务关系采用有界机制；E 计算历史/规则日历版本/待复核重算深化暂缓，不自动改期 |
| SK09 沟通与交付 | 人工编辑或上传的 Document 简报、实际交付版本/对象/时间/渠道/凭据、独立客户回复 | 自动汇总暂缓；导出与人工登记发送保留，无门户/自动邮件前置 |

这些产物进入同一事项流程和既有页面，不按技能数量另建九个子系统。界面遵循第 9 节；已有客户、财务、审批与归档能力按原业务语义保留。

## 4. 三类 RAG 的业务边界

| 范围 | 回答的问题 | 必备元数据与控制 |
| --- | --- | --- |
| 当前事项材料 | 发生了什么、谁说了什么、依据在哪里 | Matter、具体 Document 版本、锚点、解析覆盖、材料/AI 权限 |
| 获授权法律资料 | 适用哪些规则和裁判、相关时间采用哪个版本 | 法域、机构、资料类型、效力角色、相关日期、有效期间、查询日期、原始 ID/链接、实际权益 |
| 个人/律所经验 | 类似工作怎样处理、可用什么方法和模板 | 原始来源、脱敏/审核状态、适用条件、受众、修订和复审日期 |

三类资料共用业务与来源契约，默认用内置处理与授权范围内检索，可选接入 RAGFlow 或法律服务 MCP。来源性质分别显示。可使用用户获授权法律资料包开展研究；实际外部服务按所选配置与权益验证。W09.2 不再作为其他开发或 Server 发布门禁；未实测不能记为商业法库接通，网页订阅不自动等于 API/缓存/再处理授权。

三类来源是现有契约，不要求本期建成三类新生产流程。W09.3 暂缓期间可没有经验知识来源；FirmFile 既有资料、模板和权限继续使用，不能据此宣称已完成脱敏/专业审核。RAGFlow 与知识发布、方案、任务、期限和交付没有直接业务前置关系，默认沿内置解析和现有正文检索；显式选择外部服务后的失败仍如实处理，不自动换服务。

## 5. 最小增量设计原则

- **MatterBrief 为聚合视图**：从当前授权范围内的目标、决定、风险、任务和交付记录计算，不另存一套案件状态与负责人。
- **目标、指示与决定是业务记录**：利用现有范围/描述字段，补版本化指示和方案决定；保存来源、作者、确认人、时间和替代关系。聊天摘要不直接成为客户授权。
- **Document 即版本身份**：沿用每行一个版本，不新造平行 DocumentVersion 系统；索引与引用依附当前 Document 身份。
- **EvidenceItem 为证据要点主对象**：增多来源和要点之间的支持/反驳关系；技术实现不要求图数据库。
- **Task/WorkResponsibility 继续负责行动**：扩等待与依赖；等待不暂停法定期限，外部等待对象不替代内部负责人。
- **复核复用现有服务与版本状态**：Personal 适用本人确认策略，Server 适用团队审批资格与路由；AI 建议经结构化校验与明确人工确认后调用领域服务，不新造通用直接写入通道。
- **DeliveryRecord 连接审核与实际交付**：绑定确切成果版本，人工登记交付证据；下载、发送和客户确认分别记录。
- **技能是有版本的工作规格**：工具、模型与提示词可以替换；执业资格、最终判断与客户授权由人承担。

## 6. 完整场景验收包

M0 准备至少两类合成或明确获授权的民商事工作包：一类诉讼事项、一类仲裁事项；预先由专业复核人标注目标、关键事实、反证、缺口、来源与预期成果。共同覆盖合同、交付凭证、聊天记录、付款流水、法院/仲裁来件、反向材料和材料新版本。测试资料、实际客户材料和模型原始输出不提交公开仓库。

首发材料支持矩阵在 M0 冻结、M2 验证：文本/扫描 PDF、PNG/JPEG、DOCX（含普通表格）、TXT、CSV/XLSX 基础单元格值；分别登记真实页/段/单元格定位方式、处理覆盖和错误。CSV/XLSX 不承诺重算公式、执行宏或完整保留复杂版式；文件中的显示/缓存值与公式、无法读取的内容需区分。不支持的格式、加密/损坏文件、失败页及截断不能伪装为完整解析。专业判定与具体场景编号在[实施计划第 6 节](WORKBENCH_PLAN.md#6-验收与审查范围)登记。

当前工作包只在 Server 部署网页执行，使用真实认证会话、角色、业务权限和审批制度。Personal 及其本人确认/迁入验证均搁置；现有历史身份和确认记录保留，不能推断补造。

1. 记录客户目标、费用/时间约束及委托范围；沿用收案与冲突门禁。
2. 批量导入原件；出现扫描失败页、重复文件和长文时，覆盖状态可解释。
3. 形成事实时间线和争点表，逐条打开来源，列出反证和待补材料。
4. 研究一个争点，区分事项事实、法律资料与经验，保存适用日期和查询状态。
5. 使用已有文本记录方案、律师建议和真实客户指示；更正保留旧版本，不要求结构化比较。
6. 生成带来源分析草稿及一份模板文书；核对引用支持关系，执行真实审核路径。
7. 建立负责人、轻量同案依赖和等待/检查日；复用现有期限/提醒/人工保护，任务安排不改法定日。
8. 律师人工编辑或上传客户简报，沿原审批导出，登记固定版本的实际交付及独立回执。
9. 上传材料新版本，确认旧引用不漂移；过时分析和审核提示重新核对。
10. 完成既有收费、结项与归档流程；所用成果版本与交付记录可还原。
11. 在处理任务期间撤回一份材料，核查检索、模型外发、历史与引用边界。Server 同时验证成员撤权；Personal 工作区/本地通道验证搁置。
12. 在原件/数据库/任务和解析/索引/生成边界有界验证中断恢复与旧租约隔离；已启用远端服务另验迟到、重复和取消待确认。恢复范围包含实际使用的数据库、原件、配置与密钥，核对权限后开放检索。未配置远端服务不阻止本地恢复。
13. 实际启用向量嵌入时，切换同维度但不同 provider/模型的嵌入配置，验证新代次构建、失败恢复和完成后的切换；不混用不兼容向量。
14. 从正式候选 release 取得 Server 产物，先在所有可选服务关闭时完成认证、材料原件、手工成果和普通业务。再按实际已配置服务逐项验证；断开服务不影响普通业务，相关能力明确不可用，不伪造结果。Personal 不列入本期验收。
15. 检查事项列表、事项详情、材料原文、起草/复核和设置页：正文及关键日期优先、操作可找、引用可回查；没有装饰性指标墙或默认多代理聊天阵列。Personal 入口验证搁置，不作为当前关闭条件。

## 7. 如何判断产品有效

先记录同样工作包的人工基线，再测新流程；不预先宣称固定效率提升或 Rust/TS 性能倍数。

| 指标 | 观察方式 |
| --- | --- |
| 恢复上下文所需时间 | 间隔数日重新打开事项，找出目标、决定、风险和下一步 |
| 材料到时间线耗时 | 从导入开始，到律师核对后的时间线可用 |
| 事实与反证遗漏 | 对照律师标注的关键事实、矛盾、缺失材料清单 |
| 引用质量 | 分开检查“能否定位”“版本是否正确”“是否支持对应论断” |
| 草稿核查和返工 | 记录核对耗时、关键修改及不可采纳原因 |
| 推进连续性 | 等待项是否有内部负责人、下次检查时间和明确处理结果 |
| 交付质量 | 文书、证据目录、简报的返工；交付与客户确认是否可追溯 |
| 使用与恢复 | 用户能否自行安装、备份、恢复、更新；休眠后状态是否清楚 |

发布硬门槛：不得出现已知的越权披露、空授权放大、引用版本漂移、过时任务发布、未确认正式写入或不可恢复的数据丢失。Server 实际产物的核心业务、部署与恢复必须通过；Personal、W09.3/B/E/F 深化与 C 通用机制，以及可选第三方服务的未配置/未联调均不构成系统门禁。对外声明某提供商或 AI 能力已通过，仍需该项真实证据。性能暂不设阈值，不以聊天次数、生成字数或菜单数替代质量。

## 9. 界面：内容优先，减少装饰

用户明确要求“不要 UI 味道太浓”。界面以办案资料为中心，让人先看到案件内容、证据、判断与下一步。保持 LawLink 原有样式，整体视觉改版后置；2026-11-16 用户进一步要求立即审查并修复难理解的按钮和操作路径，与业务开发并行。以下设计与验收约束适用于现有页面，不另造演示页面或视觉体系。

| 场景 | 主要内容与动作 | 呈现约束 |
| --- | --- | --- |
| 打开应用 | Server 经真实认证进入工作台 | 登录、业务角色与系统管理边界清楚；Personal 搁置，不纳入本期入口和验证 |
| 今日工作 | 到期事项、等待、最近办理；可直接继续 | 使用简短列表，必要时按日期/事项筛选；不默认摆满统计大卡、仪表盘和无待处理含义的健康分数 |
| 事项列表 | 名称/当事人、程序状态、负责人、关键日期、下一步 | 紧凑可扫读的行和稳定列；不要每一字段再套独立卡片、图标、胶囊或彩色背景 |
| 事项详情 | 当前程序、目标/最近决定、关键风险、材料与待办 | 主次清楚，详细依据就近展开；团队信息只在相关模式显示；同一数据不多处复制 |
| 阅读与核查 | 原文、定位引用、笔记/证据要点 | 正文占主要空间；点引用再打开原文侧栏或分屏，返回位置不丢失；处理失败页明确可见 |
| 起草与复核 | 可编辑正文、来源、缺项、实质修改 | 类似文档编辑和审阅，不用聊天气泡包住整篇成果；确认/交付状态用文字说明 |
| 专业技能 | 整理事实、研究争点、起草、核查、客户简报 | 放在对应工作场景；没有十二个“专家人格”的首页卡墙，也不暴露编排/模型实现细节 |
| 设置 | 工作区、备份、模型服务、必要资料 | 基础信息先出现，高级参数折叠；配置失败给原因和下一步；Server 按需配置独立 API，Personal 搁置 |

视觉以浅色底、易读正文、明确层级、细分隔线与有限强调色为主；减少渐变、大面积阴影、悬浮卡片、过大标题、无业务意义图表和持续动效。长篇材料优先阅读宽度和段落节奏，列表保留合理密度；不把“克制”做成全灰、难辨识或信息拥挤。

一屏明确一个主要动作，次要操作就近放置。仅在有风险、待确认或失败时使用显著提示，普通状态不占主视觉。支持键盘、可见焦点、可读对比度和缩放；状态不只用颜色，错误保留用户输入，等待有可理解的进度/取消/恢复入口。

验收以真实工作为准：能找到案件、读清原文、核对来源、知道等待谁、完成下一步，并明确区分草稿/本人确认/团队批准/实际交付。用空白、普通数据、长文本、异常与键盘检查；窄屏暂不纳入，不凭精修截图认定完成。本节覆盖后续设计；旧 UI 文档仅在 Git 历史保留为既有实现背景，不能覆盖本次用户要求。

### 9.1 逐模块研究与用户合理性检查

2026-11-16 用户要求：每个模块开始开发时先看参考项目如何设计 UI、处理业务，再审查本项目用户的实际使用；界面减少冗余和多余解释，用布局本身表达交互。以下为持续实施约束，参考证据集中在[研究依据](RESEARCH_AND_DECISIONS.md)。

| 检查问题 | 设计与验收要求 |
| --- | --- |
| 用户正在办什么事？ | 入口跟随事项、材料、待办或成果；页面默认展示任务内容，不先介绍模块概念。首次空白状态给一个能开始的动作 |
| 用户能否看出操作对象？ | 范围选择靠近列表，行操作靠近对应材料，批量操作只在选中后出现；按钮名称表明动作，不靠整段说明解释作用域 |
| 主要动作是否清楚？ | 工作区域有明确主次；同一主按钮不在顶栏、页头和卡片中重复。低频动作收进就近菜单，关键任务入口保持可发现 |
| 状态能否帮助继续工作？ | 在对象旁显示当前状态、具体缺口和恢复动作；处理中、部分完成、失败、待核对分别表达，常规正常状态不过度强调 |
| 用户能否完成核查？ | 引用打开真实原文和对应位置，主内容与依据并排或就近展开；来源查看/返回后保留位置，不能要求用户手工找回刚才的论断；窄屏暂不纳入 |
| 这些文字是否必要？ | 标签回答“是什么”，按钮回答“做什么”；重复二者的副标题和常驻教学文字删除。格式限制就近简述，详细帮助按需打开 |
| 减少文字后是否遗漏重要信息？ | 必要字段标签、可访问名称、错误原因及修复、未读范围、影响权益/数据的确认必须保留；状态不能仅靠颜色或无标签图标 |
| 操作后能否继续？ | 成功后就地更新状态并保留上下文；失败保留输入，提供重试或人工接续。Personal 不出现账号/团队流程，Server 继续执行实际权限 |

材料模块的首个布局约定：紧凑材料行显示名称、版本、处理覆盖及必要异常；选中后阅读原文，事实或成果中的引用就近定位。解析覆盖与本次分析实际使用范围分开，不能因为某份材料已解析就显示“全案已读”。这些是待 UI 集成的验收要求，契约测试通过不会将界面标为完成。

**共享界面约束（2026-11-16 用户纠正）：** Personal 与 Server 使用原有 LawLink/LexOrder 同一套页面、导航和业务流程。Personal 直接以稳定本机操作者打开工作台，Server 经登录进入；个人模式隐藏账号、人员、团队和组织授权功能，保留原有事项、客户、日程、财务、文书、归档、外部联系人及必要业务配置。AI/OCR、模板、期限规则等配置继续复用已有表单，不能随“后台管理”入口一并丢掉。个人确认如实表现为本人确认，团队审批仍按原有资格；不假造管理员或第二人。M1 的独立材料技术页不作为个人版产品入口，检索能力后续进入既有事项材料区。

**实施优先级（同日后续纠正）：** 保持 LawLink 原有样式，业务实现和已复现的可用性修复并行。Frappe CRM 继续作为对象导航、列表/详情连续性与就近操作的参考。用户随后将界面审查委派其他 agent，本执行组停止全站审查，保留已完成按钮、定位、焦点和状态修复供专项接续，负责新业务和 M2 收口；新业务仍验证入口、操作对象、保存/重开及必要返回路径。Personal 已搁置，当前只处理 Server 页面；避免独立聊天首页、营销欢迎区和重复解释卡片。持续实施规则见 AGENTS §5.2，M2 完成证据见计划 §8.9。

**最新范围调整：** 用户明确窄屏暂时不考虑；当前工作和 M2/M3 验收不再安排窄屏专项，既有观察保留，不据此扩大界面测试。

**现有业务表单约束（Server 浏览器复核）：** 校验展开的字段在用户编辑时保持展开，连续输入不得因字段数组重建而丢失焦点。客户列表、详情及联系人维护的编辑入口与既有服务端授权一致，系统管理员身份不替代业务权限；列表摘要不能直接作为整份客户主档的编辑数据，打开编辑前取得完整联系人，读取失败时保留原记录并提示重试。以上修复沿用现有样式，不增加常驻说明或放宽提交校验。

**新增业务入口约束（用户页面反馈，按最新工程约束修订）：** 左侧「案件」打开具体事项后，「档案与摘要」直接呈现当前授权的事项摘要和目标与指示，「办案与材料」承载原件、处理状态、证据要点和事实时间线；「客户」详情继续承载沟通、跟进及客户动态。管理后台入口统一为「AI 与外部服务」。案件地址使用实际完整 internalCode；不保留旧 ID、大小写后备或缺编号的兼容路由，现行入口统一生成规范地址，不猜测相近编号。既有双路由的实现与浏览器证据保留为历史记录，不再作为兼容验收要求；本次目标见架构 C02。通用 404 不能作为权限诊断。团队概况缺少记录权限时不读取记录服务，且不扩大材料或写入资格。

**按钮与返回路径（用户新增反馈）：** 动作名称说明动词和对象，不把目标/指示、经办记录与事实要点都简称「记录」。来自某一区域的编辑或查看动作须定位相应内容；无可编辑对象时不提供会打开另一对象的入口。同日、同名来源在当前读取资格内显示时间与短摘要，不能依靠猜测选原记录；弹窗关闭后恢复触发位置，键盘用户可继续原任务。无程序、无环节、空材料分别采用真实状态文案。服务输入检查使用「检查所选材料」「未处理部分」等业务用语，明确本次是否调用 AI，不把解析或可准备范围写成模型已读。

**核心界面连续操作（2026-11-16 收尾）：** 首页焦点独立显示最早未完成期限（包含逾期），不受近期日程预览条数限制、不以开庭代替期限；今日/逾期按上海日界判断，近期日程覆盖今日起连续 30 个日历日。案件收案日期先在弹层填写起止、点击「应用」统一筛选，清除同步清空输入与已应用范围，未应用草稿不改变结果。沟通/研判入口与实际记录写入资格一致，环节研判数只计同环节研判笔记；吸顶摘要将全案节点与当前程序案号分组标明。客户编辑和沟通的受控退出保护未保存输入，关闭回发起位置，保存后原行移除则回页面现有稳定入口；字段可见标签与控件绑定。客户待跟进和沟通历史在桌面并列、各自分页，长正文按条展开；可选服务配置有未保存修改时隐藏原配置的测试结果，不暗示新草稿已验证。均沿用现有组件与业务守卫，实际验证边界记于计划 §8.15。

**事实性质与记录核对：** 「事实／主张／分析／争点／待核实」描述内容性质；「记录待核对／记录已核对」描述某一版本的人工核对，两者不得混成真假结论。核对弹窗展示具体记录、版本和性质，明确不等于认定事实；修改或调整来源后重新核对。要点用可见「查看要点／查看与编辑要点」入口，不把可操作性藏在普通标题中。

**人工创建失败重试：** 同一次要点保存若响应中断，表单保留草稿，重新保存不得生成重复正式要点。服务已保存而用户又改了内容时，必须明确提示先查看已有结果，再按修订处理；不能静默丢弃新输入或自动另建。关闭后重新发起的记录是新的创建意图，重试仍核对当前办理和来源资格。

该要求已由稳定请求键、作者/请求唯一约束、服务端固定载荷指纹及当前资格复核实现；新增真实 PG 与表单生命周期验证见[计划 §8.9](WORKBENCH_PLAN.md#89-m2-最终收口账本2026-11-16)。

**离线材料读取检查（W08 输入诊断增量）：** 用户在「办案与材料」明确勾选具体版本，最多 50 份；不默认检查全案。选择区标明不限当前环节，列出的仍是本页程序范围内的可用材料。检查只读取内置已有文本和来源状态，分别呈现可读取内容、本次可用于审查的范围、失败/未识别/截断及省略明细；明确「本次未调用 AI」。没有模型配置仍能检查，失败可以重试；不可读材料不保留旧名称或诊断。本增量不等于已完成实际 AI 供给、候选采纳或持久运行。

### 9.2 组件复用与内置样式优先

2026-11-16 用户在案件操作审查中明确指出时间线渲染不正确，并要求参考所用框架的内置样式、尽可能避免自行重写。本条立即约束本期 Server 的新增界面和缺陷修复；整体视觉改版后置不意味着保留已经失效的布局。

**实现顺序：现有公共组件/业务模式 → 标准变体、尺寸与主题令牌 → 组件组合 → 必要且有边界的业务布局。** 实际底座以 [components.json](../components.json)、[公共组件](../src/components/ui)及[业务模式组件](../src/components/patterns)为准。当前 Dialog 使用 Radix；参考官方示例时选择对应底座，不为跟随默认示例重新安装或切换整套 UI。

| 场景 | 首选实现 | 必须保留的行为与限制 |
| --- | --- | --- |
| 按钮、标签、状态、输入 | 已有 Button、Badge、Input、Textarea、Select 等及其标准变体 | 复用主题与可访问状态；业务类名主要表达布局，不另造同用途基础控件 |
| 编辑、确认、来源查看 | 已有 Dialog/Sheet 与 patterns 中的表单、确认、复核模式 | 沿用遮罩、焦点、键盘与关闭逻辑；未保存内容保护、异步失败及返回位置明确 |
| 长列表与正文 | 先使用现有容器的滚动能力；确需独立区域时复用 ScrollArea | 避免多层滚动；长标题、长中文、引用及元信息能换行，关键动作可达 |
| 事实时间线 | 组合已有 Dialog/Sheet、Button、Badge 与自包含列表布局 | 当前组件目录没有专用 Timeline；不另建完整时间线框架，不把事实事件画成已完成步骤条 |
| 页面与弹窗共享内容 | 共享组件自身声明必要布局，使用已有语义令牌 | Portal 内不依赖 `.mo-dossier` 等页面祖先；同一列表移入弹窗后间距、层级和换行必须保持 |
| 确有组件缺口 | 先核查已安装组件及官方组成方式，再记录缺口和采用方式 | 优先最小组合；新增组件或局部样式有明确必要性，不以整套换皮解决流程问题 |

时间线的三种语义分别验收：**事实时间线**按事件发生日期显示，未知日期单列；**办案记录**展示沟通、研判、完成任务等操作记录；**程序/环节进度**表达办理阶段。三者统一样式基础，但不互换日期或完成状态。事实的性质“待核实”与版本“已核对”是不同维度，不能在一个无标签状态串中造成事实已查明的误解。

最低验收：同一要点在页面内和真实弹窗内均有正确的标题/正文/来源/元信息层级；短文、长文、空白、失败、历史版本和受限来源均可解释；窄屏暂不纳入；键盘可操作并回到原入口。样式修复不得改变来源权限、旧引用、人工确认或日期排序。

本次参考已读取的官方 [shadcn Radix Dialog](https://ui.shadcn.com/docs/components/radix/dialog)、[Badge](https://ui.shadcn.com/docs/components/radix/badge)及 [Radix Dialog Portal](https://www.radix-ui.com/primitives/docs/components/dialog#portal)，并与仓库实际组件核对。官方 Portal 默认挂载到 `document.body`；本项目时间线的具体样式缺陷与浏览器证据登记在[计划 §7.9](WORKBENCH_PLAN.md#79-案件操作全流程审查与组件约束2026-11-16)，本段规范不表示该缺陷已修复。

#### 9.2.1 已交付的任务分类与连续操作（2026-11-16）

### 9.3 案件操作的分区与交互修复规格

**2026-11-16 用户最新澄清：**一个案件应有唯一、清楚的案件整体状态；全案总览汇总案件，案件下可有多个程序，各程序再组织环节、材料和办理内容。程序或环节的查看选择不能直接改写案件状态或冒充实际办理进度。若现状缺陷较多，允许依据事实在受影响业务范围内做结构性重构，见 [AGENTS §5.4](../AGENTS.md#54-单一现行实现与适度工程2026-11-16-用户追加)。当时优先分析案件状态和核心界面；文档连续编辑只是痛点示例，本次整体规划不据此立即开发编辑功能。审查与参考见[计划 §8.13](WORKBENCH_PLAN.md#813-案件状态与核心界面审查2026-11-16)及[研究 §3.15](RESEARCH_AND_DECISIONS.md#315-案件状态与核心界面的多项目审查2026-11-16)。

**已认可的呈现方向：**全案总览展示总体状态、实际程序和事项级保全；选中程序或环节后展示其真实关联材料、任务与已记录进度。事实/研究、记录、期限及未归属对象按其真实范围呈现，不能因选中而伪造归属；查看不改变业务状态，但允许正常读取审计。本期不增加程序前序字段、依赖表或强制前序门禁。开工前缺口见[计划 §8.20](WORKBENCH_PLAN.md#820-合并后的案件工作区优化计划2026-11-16)，本批实际修改、验证与剩余范围见[计划 §8.21](WORKBENCH_PLAN.md#821-当前主线的-m3-接续执行2026-11-16)。

**本批程序状态和范围行为：** 全案状态与程序状态分别展示，选中程序/环节只改变查看范围。新增程序不自动开始或结案；仅信息程序先显示“状态待核对”，旧记录没有实际终结日期时也不据默认状态冒充已结案。旧默认 CONCLUDED 且没有实际终结日期的信息记录，办理动作使用“记录办理中”和必填“状态核对说明”，不称已结案后恢复；新 PENDING 信息程序的说明仍可选。由有权人员明确记录开始、实际终结或恢复办理；恢复填写原因，变更期间权限、归档或版本发生变化则拒绝本次保存并保留输入。结案案件新增或恢复受托程序须先走原重开动作；多个同类型程序实例按实际对象存在，不由类型、顺序决定法律先后。新增成功进入创建的确切程序，未完成请求的迟到响应不改写已经切换的位置。

材料和任务只按已存外键筛选，未归属材料/事项级任务保留入口；环节日期和已有进度记录如实显示。事实/研究与办理记录为全案范围，期限/庭期为程序范围，保全为事项级并沿其本身的读取资格；不凭名称或日期把对象归给环节。无日程读取权限明确显示，不与“没有日程”混用。

**2026-11-16 用户要求先落修复计划，并追加两项界面原则：业务不能全堆在一个界面，应当合理切换；界面逻辑主要由布局传达，减少解释文字。** 以下是现行交互要求，按受影响切片实施；代码、组件测试、真实桌面操作与律师专业验收分别记账，不把部分实现当成整体验收通过。继续使用现有 LawLink 样式、shadcn/Radix 组件和业务身份，保持四个主页面入口，不新建平行工作台或全局菜单。事实与修复编号见计划 §7.9/§7.10。新增工程约束统一见 [AGENTS §5.4](../AGENTS.md#54-单一现行实现与适度工程2026-11-16-用户追加)：先核实缺陷和现有能力，单一现行实现、无兼容/fallback；核心端到端先行、组件模块化、避免多余抽象/投影与重复 hash。

此前规划的实施链为“案件→具体材料→要点/来源→返回”，不要求下表全部能力同时完成才提供可用流程；当前按用户最新指令先审查案件状态与核心界面。版本族整理、分区编辑、财务和归档按后续完整任务逐步接入；不以临时兼容路径跨越未完成能力。

#### 布局与文字的验收约束

- 顶部标题只标识对象或当前任务；范围控件贴近对应列表；选中态说明当前位置；列表行旁的状态与动作说明下一步。正文位置留给材料、事实、金额、日期和必要业务字段。
- 一个任务区有一个显著主动作；低频操作收进该对象的菜单。批量动作仅在明确选中后出现，并提供“已选”视图，不能让被筛选隐藏的材料悄悄参与处理。
- 不加重复副标题、功能介绍卡、常驻步骤说明、大面积统计卡、营销式欢迎区、装饰时间轴或无意义动效。空态使用短句与一个可开始的动作，筛选无结果给调整筛选入口。
- 不删除字段标签、可访问名称、错误原因/补救、未处理范围及风险确认；这些说明放在发生问题的对象或确认场景。正常状态保持简短，不能把必要信息全藏进 tooltip。
- 首屏不同时展开所有业务。当前桌面列表与详情使用同一业务语义与数据，窄屏暂不展开设计/验收；不靠固定三栏或横向溢出撑开布局。切换、关闭和删除后有合理的键盘焦点。
- 视觉验收用真实普通/长文/空白/失败的桌面页面，操作验收覆盖切区、保存、刷新、后退和来源往返。仅改文字、仅隐藏 DOM 或截图变好，不等于逻辑与操作流程已通过。

#### 9.4.1 当前实现入口与明确状态（2026-11-16）

办案工作区现分为“材料”“事实与研究”“任务与期限”“办理记录”。“事实与研究”内分事实/争点与法律研究；“办理记录”内分原办理进展与客户交付。已经进入的任务组件保持自身草稿，来源查看、详情关闭和对象切换沿各自确认边界；未保存正文不写进 URL。

| 对象 | 当前定位字段 | 确切行为 |
| --- | --- | --- |
| 研究 | workPane=facts、factsView=research、research 或 issue | 正常创建/修改/核对的本事项 ISSUE 均可选入，保存固定采用时内容、来源与核对状态；保存后定位确切研究修订。争点变化时更新选项但保留研究输入，读取失败或失权不换另一研究 |
| 文书/问题 | document、reviewIssue；审批另用 type=DOCUMENT_APPROVE、id | 正文、人工复核、版本分区；同族版本逐件核权，历史版本不提升为最新版；成功关闭清除旧定位 |
| 任务 | workPane=tasks、task | 全案数据与原责任板使用同一 Task；程序/环节按真实关联筛选，无环节的事项级任务通过全案或未归属入口可达；到期未结束等待有“待检查”标志及筛选 |
| 交付/事件 | workPane=records、recordsView=delivery、delivery、deliveryEvent | 回到原固定清单及事件；重新准备需明确确认，保存失败保留本次输入；客户动态只链接实际接收客户的原记录 |

具体文书无明确版本关系时，正文与原审批仍按原资格可读；读取不补写族，建族前不能关联已有修订。符合权限、最新版和业务守卫时，用户提交新版的现有事务以前版 ID 建族；审查报告等固定记录仍受原限制，不凭名称猜测另一份材料的版本关系。研究核对、人工问题处理、文书批准、入卷、导出、发送登记、收悉与内容确认各自显示；人工发送没有凭据时明确标示其登记性质，凭据失权时不继续下发相应登记正文。

研究不要求争点已经核对或已有来源才能开始；有来源时每个来源都须当前可读。研究详情显示固定采用时的争点内容、来源和核对时点，后续争点修订或仅核对状态变化分别提示，均不改写旧研究。另存修订默认明确保留原研究输入；选择新当前争点时重新核对内容版本及核对时点。来源入口回到原来采用的具体材料，不能静默跳到新版。

等待检查日只用于内部跟进。现有扫描器针对到期且未结束的等待发送站内通知，复核当时有效责任与权限并去重；改期、结束等待、停用或撤权后不沿旧请求发提醒。等待通知不进入邮件摘要，检查日不改法定期限，也不自动完成任务。

#### 9.4.2 人工判断、期限版本与当前读取资格（2026-11-17）

- **冲突检索与人工决定分开。** “按当前主体重新检索”即使没有命中也显示待人工判断，由有权经办人明确填写结论和理由。正式收案批准转案可继承当次实际批准判断。旧记录缺少真实决定依据时显示“待人工核对”，不改写原历史；后来新增命中或范围变化时，重新显示核查入口。旧页面提交不能覆盖别人已经保存的判断，失败保留本次说明。
- **期限确认针对所见日期。** 确认和人工调整携带用户所见版本；日期、事项归属、当前资格或归档状态已经变化时拒绝保存，提示刷新核对，保留调整输入。人工调整保留真实原日期、操作者和理由；原确认/人工调整保护继续有效，不增加复杂重算平台。
- **处理中的材料也受当前权限约束。** 下载、原生类型预览及 Office 预览在读取/解密/转换完成后、返回正文前再次核验会话、当前材料及实际来源。处理期间撤回材料、移除事项成员或撤销会话后不继续返回正文，也不登记成功读取。独立审批人员仍只获得具体送审文书的合法正文资格，不能因此读取来源或导出整案。
- **交付导出从实际部署入口发起。** 合法入口可保存后的固定清单导出；不同 origin（包括 localhost 与 127.0.0.1 这类不同入口）不能互相代替。导出、真实发送登记和回执继续分开；重试同一次导出不新增第二个事件。下载和 Office 预览采用私有、不存储的响应策略。

本批真实 HTTP 已覆盖密码登录、原件字节、预览、独立审批正文与来源边界、固定交付 ZIP/重试、团队撤权、来源撤回及停用后的原会话；处理期间撤权另由真实 PostgreSQL 路由/服务测试验证。研究、分析稿生成与送审等 fixture 使用真实业务服务，但其调用不计作 Server Actions 的 HTTP 验收；归档与整案导出只覆盖匿名/无权 HTTP 路径。成功归档 ZIP 仍仅有 §8.21 明确缺项的合成例外归档服务证据；本批未验证成功归档或整案 ZIP 的 HTTP 路径。组件测试不代替浏览器，合成资料不代替律师专业复核。

## 10. 技能是什么

一项技能是**有适用范围、输入前置、明确步骤、结构化产物、证据、复核责任和评测方法的工作规格**。它应帮助律师完成一项可交接的工作，结果进入事项、材料、研究、文书、任务或交付记录；不能只留下无法还原依据的聊天文本。

技能定义共用，按运行模式适用；多人责任转移、成员资格和撤权场景仅属于 Server，不构成 Personal 的人员管理或认证前置。团队中的承办、研究和复核分工由现有角色及授权决定；个人版无需认证，仍保留本机操作者的明确确认动作和审计。产品不生成虚构的“合伙人已批准”或把多个 AI 角色互相同意当成人工复核。

首发适用中国大陆民商事事项；通用研究、表达与协作方法可参考海外样本。司法辖区、准据法、语言、业务时区和数据处理地区分开。尚无对应法律来源与验证样本时，技能可以整理问题和待办，不能宣称具备该法域的实质分析能力。

## 11. 统一执行契约

### 11.1 所有技能共同遵守的规则

| 项目 | 必备内容 |
| --- | --- |
| 身份与范围 | 服务端确定操作者、Matter、任务目的、可读材料、AI 处理资格与允许工具；不信任模型给出的权限范围 |
| 上下文 | 客户目标/指示及其确认状态、工作阶段、受众、相关法域/日期、输出语言、约束 |
| 输入快照 | 具体 Document 版本、校验值、解析/索引代次、来源类型、实际送入模型的片段与未处理范围 |
| 执行记录 | 技能/提示/模型版本、工具及查询、开始结束、用量、失败/取消状态、复核与采纳结果 |
| 输出 | 结构化成果、主张对应来源、反向证据、假设与未知、覆盖说明、候选行动与复核项 |
| 状态区分 | 草稿、待核实、人工复核、业务批准、实际执行/交付、客户确认分别记录；中止或部分完成不伪装成功 |
| 来源使用 | 区分案件材料、法律资料和经验；标明原始材料、客户陈述、推断及确认状态；无法核实的引文不充当依据 |
| 写入 | 运行记录与私有候选草稿可在本次请求授权范围内自动保存；新增/修改正式业务对象、版本及状态，或对外交付，须经结构/引用校验与对应人工确认后调用领域服务，事务内重验权限、目标版本、状态与幂等 |
| 变更 | 材料版本/授权/指示发生变化时标记受影响产物；旧引用可还原，已批准结论不静默改写 |
| 执行限制 | 设置材料/调用/用量预算、超时、取消和恢复；资料正文只作证据，不得改写系统权限与工具规则 |

“当前授权范围”不能靠提示词保证。服务端在检索、取全文、送模型、结果可见、打开引用与正式写入时执行对应校验。后台作业保存发起人及执行目的，运行时重验；系统管理员资格、案件概况可见和财务权限不能相互替代。

### 11.2 TypeScript 契约草图

以下类型用于说明边界，最终由 Zod 和现有对象类型收敛；不是已经加入源码的接口。`context` 只能由服务端创建。`sourceRef` 是经服务端解析的来源引用，不能用任意外部 URL 或猜测 ID 绕过权限。

```ts
type SkillId =
  | "SK01" | "SK02" | "SK03" | "SK04" | "SK05" | "SK06"
  | "SK07" | "SK08" | "SK09" | "SK10" | "SK11" | "SK12";
type SourceKind = "CASE_MATERIAL" | "LEGAL_AUTHORITY" | "PRACTICE_KNOWLEDGE";

interface SourceRef {
  sourceRef: string;           // 服务端可解析的具体版本及真实锚点
  kind: SourceKind;
  relation: "SUPPORTS" | "REBUTS" | "CONTEXT";
}

interface SkillContext {
  actorId: string;             // 本机操作者或已认证成员，服务端映射现有 User 关联
  runtimeMode: "PERSONAL" | "SERVER";
  matterId: string;
  authorizationSnapshotId: string; // 记录审计范围，不能代替实时授权
  sourceManifestId: string;         // 实际版本、输入片段及覆盖
  instructionRevisionId?: string;
  jurisdictions: {
    governingLaw?: string;
    forum?: string;
    procedureJurisdiction?: string;
    relevantDate?: string;
    businessTimeZone: string;
  };
  outputLanguage: string;
  audience: "INTERNAL" | "CLIENT" | "EXTERNAL_DRAFT";
  approvedToolIds: string[];
  maxToolCalls: number;
  maxInputTokens: number;
  timeoutMs: number;
}

interface SkillResult<TArtifact, TAction> {
  skillId: SkillId;
  skillVersion: string;
  runId: string;
  status: "DRAFT_READY" | "PARTIAL" | "NEEDS_INPUT" | "FAILED" | "CANCELLED";
  artifact: TArtifact | null;
  claims: Array<{
    id: string;
    text: string;
    basis: "CLIENT_STATEMENT" | "DOCUMENT_STATEMENT" | "INFERENCE" | "LEGAL_RULE";
    sources: SourceRef[];
    reviewState: "UNREVIEWED" | "VERIFIED" | "DISPUTED" | "UNVERIFIED";
  }>;
  coverage: {
    sourceManifestId: string;
    processedRefs: string[];
    omitted: Array<{ sourceRef: string; reason: string }>;
  };
  unknowns: Array<{ question: string; impact: string; suggestedNextStep: string }>;
  reviewChecklist: Array<{ item: string; blocking: boolean }>;
  proposedActions: TAction[];  // 每技能的允许动作联合类型，无通用任意写入
}
```

模型不能自行把 `reviewState` 置为 `VERIFIED`，也不能伪造复核人。上例统一承载已存记录和新候选；新输出由服务端固定为待核实/待审阅，人工确认状态只能经相应业务服务转换。用户无权看到的材料名称、标识或失败详情也不进入 `coverage.omitted`。

动作类型按技能白名单定义，例如新增证据要点候选、生成任务候选、关联文书草稿；每项必须包含目标对象及版本/前置状态。通过一次技能审核不等于批准所有后续动作，正式文书复用现有审核服务与版本状态，Personal 适用本人确认策略，Server 适用团队审批资格与路由；交付需要真实发送或人工登记证据。

### 11.3 注册、执行与评测

M3 人工工作链不以通用技能 registry、执行器或完整 AiRun 为前置。实际启用自动技能时，再按使用场景评估版本化契约、所需读工具、权限、日志、取消和评测；复用现有模型 provider、JobQueue 与业务服务，不引入用户任意脚本或通用多代理平台。SK03 的既有法库适配、SK06 的模板与 SK08 的调度仅是各自局部基础，不代表自动技能已完成。

若未来实施 AiRun，应保存实际使用的技能、来源版本及输入范围；敏感输入/输出沿用私有存储和权限，不把原始案卷、提示内容或个人信息提交源码库。模型、分块、工具或技能步骤变化时，仅重验受影响的质量样本。

## 13. 分项工作规格

### SK01 事项上下文与委托目标

- **前置**：有权读取的 Matter、客户目标、委托范围/排除项、交付物、时间及预算约束/假设、决策人、客户沟通/指示、最新决定、任务、期限和成果状态。各约束有来源及确认状态，没有明确目标或金额时列待补问题，不补造。
- **步骤**：按时间和版本整理指示；区分目标、约束及律师建议；提取最近改变、主要风险、等待与下一步；逐项回链原记录；按本次使用者权限生成聚合视图。
- **输出**：`MatterBriefDraft`：目标与确认状态、范围/约束、关键事实、最近决定及理由、风险、等待对象、内部责任人、下次检查、下一步。
- **复核**：律师确认目标和范围；系统不从聊天中的设想推定客户授权，不将已有责任人复制为新的权威状态。
- **验收**：客户改变目标/范围/预算假设后旧指示仍可还原，改变不自动成为合同或收费变更；数日后重开能定位改变与下一步；财务不可见用户的简报不泄露费用。已有客户摘要与沟通/跟进连续聚合，超出当前返回窗口可继续加载，隐藏事项的计数也不披露。

**M2 客户与上下文增量（已实现，必要业务链已验收）：** 原客户详情的事项、沟通和待跟进连续分页，累计数量基于当前可见范围；统一动态逐来源复核资格。失败保稿、当前权限和迟到响应边界的 PG/HTTP/组件证据见[计划 §8.6](WORKBENCH_PLAN.md#86-m2-连续记录与事实日期执行结果2026-11-16)；实际跨页、关联事项与统一历史跳转见 §8.7。本批目标保存→更正→核对→刷新→历史/来源/摘要，以及三段 Esc 回焦见 §8.9。未把上述代表性路径扩大为客户页所有错误、窄屏和角色组合均已实测。

### SK02 事实、证据与时间线

- **前置**：材料真实版本、页/段/表格锚点、解析覆盖和可读权限。未完成 OCR 的部分保留缺口。
- **步骤**：① 读取覆盖清单与文件性质；② 提取主体、行为、时间、金额及原文位置；③ 沿用 FACT/CLAIM/ANALYSIS/ISSUE/TODO_VERIFY 五类要点，另保留陈述来源和确认状态；④ 关联同一事项的多个来源；⑤ 主动查找矛盾、反驳与日期冲突；⑥ 生成带不确定性的时间线和补证问题；⑦ 校验每个锚点确实来自当前授权版本。
- **输出**：`EvidenceDraft[]`、`TimelineDraft[]`、多来源链接、支持/反驳/矛盾关系、材料缺口及候选补证任务；日期允许范围或未知，不补造精确时刻。
- **复核**：材料记载不自动成为法院认定或律师确认的事实；转成正式 EvidenceItem 前逐项确认重要事实和关系。候选身份、逐材料来源与人工接受/拒绝/纠错历史分开；严格同一候选避免重复确认，实质变化或新反证重新复核，语义相似不自动并事实。反向材料不能因与目标不一致或旧拒绝而隐藏。
- **验收**：同一付款在聊天和流水中日期/金额不同；扫描失败页；两个同名主体；附件替换新版本。期望矛盾与覆盖可见，旧引用仍指旧版本，重复运行不重复创建已采纳要点。

**M2 人工增量（已实现，必要业务链已验收）：** 原要点编辑支持精确日、日期区间或未知，并保存原始时间表述；不把“某年夏天”或创建时间换成发生日。日期更正保留旧版并重新待核对；事项事实时间线覆盖全事项当前可读要点，保留性质、支持/反驳及来源入口，受限日期不参与分组和排序。日期/权限 PG/HTTP 证据见计划 §8.6；实际选材、保存、增补反向来源、修订、核对、新窗口重开、历史/原件及窄 CSS 视口键盘检查见 §8.9。W08 本地范围检查已完成并明确未发送 AI；自动候选记忆、持久 AiRun 和实际模型供给/召回记录仍待实现。

### SK03 法律检索与研究记录

- **前置**：研究问题、用途/受众、时限与资料/成本约束，相关事实及未知、准据法/程序法域/机构、相关日期、实际可用资料与查询权限。适用范围不清时先澄清，不能默认换成最常见法域；记录用户请求与实际检索范围的差别。
- **步骤**：① 拆解争点和检索词；② 说明拟使用的资料类型与提供商能力；③ 执行并记录查询；④ 读取和核对原文身份、版本、效力角色及时间；⑤ 找出适用条件、例外和不利依据；⑥ 将规则与当前事实逐项对应；⑦ 输出结论支持程度、缺失来源和补查动作。提供商故障、无权限和无结果分别记录。
- **输出**：`ResearchMemoDraft`：问题、范围、查询记录、来源表、规则与例外、适用分析、反向材料、未知和行动。法规条款、案例编号、裁判日期不能仅凭模型记忆生成。
- **保存与引用**：已核对或被任何成果引用的修订和采用的法源元信息固定；未核对研究也可用于草稿，但先保存确切修订，之后编辑另成修订，不把旧稿依据换成当前研究。
- **复核**：律师检查来源是否真实、相关时间是否正确、是否实际支持结论；类案的参考价值与规范性依据区分。没有原文或可核实片段的引用标为待核实，不用于关键肯定结论。
- **验收**：法规已有修订但事实发生在旧版期间；同名不同法域规则；一条反向案例；接口拒绝访问。结果应提示时点与范围，不将接口失败写成“没有法律依据”。

### SK04 争点、论证与反向审视

- **前置**：SK02 的可追溯要点、SK03 的研究结果、当事人主张和程序阶段；尚未审核的输入保留状态。
- **步骤**：把争点拆成待判断问题与法律前提；映射支持事实、反向事实和未知；分别整理可成立的双方论证；指出改变结论的关键假设和补证优先级。证明责任的具体分配必须引用已核查法律来源。
- **输出**：`IssueMatrixDraft`：争点、前提/要件、支持/反向来源、可能反驳、缺口、下一动作；不预设所有请求均有充分证据。缺口区分尚未取得、已取得未解析/未供给、已核查范围内未记载；仅有单方材料不推定对方无异议。涉及金额主张时保留原文总额、明细/公式/期间/单位及依据，机械核对只报差异，不改原数或形成财务实收。
- **复核**：律师确认争点边界、法律前提和证据评价；不以模型置信度代替胜诉概率。
- **验收**：加入一份关键不利材料后，论证和补证优先级应相应更新；未证实事实不能在另一段变成确定结论。

### SK05 策略、方案与客户决定

- **当前范围**：复用已有 OPTION/DECISION 文本、来源、发生时间、核对和不可变更正；用户可手工记录选项、理由、已知成本/时间假设及限制。
- **步骤**：查看目标和研究→记录律师建议→在实际收到回复后另记客户指示；未回复保持未决定，未知不编造。
- **输出**：现有版本化方案/决定记录；需要详表时引用人工制作的具体文书，不新建比较模型。
- **复核与验收**：建议不冒充客户同意，核对不改变指示性质；更正保留旧版，不能自动改合同、收费、批准或历史成果。
- **暂缓**：B 并排比较、打分、结构化收益/成本/时间矩阵及自动变化分析最低优先级、非门禁。参考有文本决定和销售预测，但未证明本项目所需的完整比较业务；见研究 §3.12。

### SK06 带依据的专业文书起草

- **前置**：具体事项、已选研究/事实来源、实际模板、确切主体/程序及文书写入资格。
- **步骤**：选择模板和对象→显示实际使用字段及现值→补本次文书必要缺项→人工核对→生成具体 Document；少量明确条件只覆盖真实模板。切模板/主体/程序重新取值，失效临时答案不静默复用。
- **输出**：分析稿或模板稿、具体来源版本、模板源版本及真实渲染快照；缺项分未提供/不适用/已提供，生成成功仍是草稿。
- **复核**：当前字段及专业内容由律师核对；临时值默认只用于本稿，客户/当事人主档通过原独立编辑入口修改。准备、预览、取消与失败均不隐式写主数据。
- **验收**：一份真实模板从选材/补缺至稿件重开，切对象不串值，原件/旧批准不改；沿既有送审和 SK07 完成人工复核。
- **暂缓**：docassemble 式通用自适应访谈、任意表达式/模板语言、递归跨会话依赖及 AI 自动补问最低优先级、非门禁。采用其有限条件/核对业务及 j-lawyer 的字段值核对流程，不搬 Python/Groovy 运行时。

### SK07 文书与论证复核

- **前置**：待审文书的确切版本、源材料与研究范围、适用模板、作者提出的问题、复核资格。
- **步骤**：① 独立列出本次检查范围；② 逐项核对事实、金额、日期、主体及来源支持关系；③ 检查法律依据的身份/时点/例外；④ 对照反向证据和客户目标；⑤ 检查论证跳跃、内外矛盾、遗漏与受众表达；⑥ 将问题定位至段落并给出原因与建议；⑦ 保留作者回应与实际处理，生成送审前检查记录。
- **输出**：`ReviewReportDraft`：每项问题的文书版本/位置、类别、严重性、依据、建议及待确认项；形成修订候选而非直接覆盖原文。作者逐条接受/部分接受/不接受并说明理由，关联实际修订版本/位置，有权复核人记录处理或保留未决；问题关闭与文书批准分开。
- **复核**：AI 复核报告只是审核辅助；实际确认须由真实操作者针对该版本执行；Personal 如实记本人确认，Server 按团队审批资格判断。模型间一致、没有找到问题或检索范围不足均不等于“审核通过”。
- **验收**：植入一个引用存在但不支持论断的问题、一个过时版本、一个不利事实遗漏和一个金额矛盾，检查发现/定位、作者回应及修订证据。来源更新仅提示显式关联产物待复核，未连边显示范围有限；修订后再送审不能复用旧批准，已交付旧稿保持不变。

### SK08 责任、依赖与期限推进

- **前置**：下一动作、内部负责人、现有 Task/WorkResponsibility 及必要事项资格；普通任务不强制虚构程序。
- **步骤**：保存任务→按需选择同案前置→等待时记录外部对象、所需成果和 nextCheckAt→复查→通过原责任链推进。答复结束等待，不自动完成任务。
- **D 保留范围**：采用 ERPNext 的成熟有向前置关系、环检测和任务详情选择；所有完成入口复用当前事务与资格检查。仅责任状态 DONE 满足前置，CANCELLED 不满足，也不能在批量操作中回报办结成功；取消后有权者明确移除/替换前置并留理由，重开不回滚已完成历史。不搬自动级联改期或项目平台。
- **期限范围**：使用现有 Deadline、来源/理由、规则候选、人工确认/明确调整、保护与提醒；任务安排和检查日不改法定日。日历异常/宿主日期依赖是保留入口的定点正确性问题，按实际影响修复，不新建期限平台。
- **输出与验收**：零程序事项创建任务、登记等待、刷新后从全案待办重开同一 Task，与责任板一致；无权/越案/环、取消/重开前置和并发绕过完成有定点反例，交接与重复操作沿原守卫。
- **E 暂缓**：完整规则/日历版本、计算历史、变更传播和逐条持久重算差异最低优先级、非门禁。来源改变由律师核对并使用原调整入口，不承诺自动扫描或历史复算。

### SK09 客户沟通与交付

- **前置**：受众和披露范围、具体文书版本及现有材料/财务资格。
- **步骤**：律师查看获准的现有记录，人工编辑或上传简报→保存具体 Document→核对并沿既有必要审批→保存固定交付清单→导出→实际发送后人工登记→另记回执/客户回复。
- **输出**：人工简报（进展、风险、待决定、下一步）、固定版本清单、实际接收对象/时间/渠道/凭据或明确事实说明。无凭据标“仅人工登记”，不显示已核验。
- **复核**：人工文字由律师审阅；自动页面状态不冒充对全文的核实。摘要可读不代表附件可交付，费用仍按实际资格；未确认实收和等待不得被写成已到账/完成。
- **验收**：已有文书且无任务/等待也可交付；保存、刷新和新增客户动态打开同一清单/回复；改正文走新版本，导出、发送、收悉、客户内容确认分开，更正/补发不覆盖历史事实。
- **F 暂缓**：自动跨业务汇总、受众改写、定期简报、AI 自动生成和自动发送最低优先级、非门禁。Counsel 的内部摘要保留为未来参考，现有 MatterBrief 继续只读聚合。

### SK10 交接与监督

本项多人交接、接收资格和成员撤权属于 Server 场景；Personal 可复用资料整理与本人事项巡检，不提供人员管理或伪造多人交接。

- **前置**：真实转出/接收人员、当前责任链、可读材料、最新决定、期限、等待、未解决风险与文书状态。
- **步骤**：形成接收人需要的上下文；列未完成/阻塞及下一动作；提示关键期限与资料缺口；保留接收意见及追问；依现有交接流程提交确认和责任变化。
- **输出**：`HandoverPackDraft`、接收检查表、待澄清问题和反馈记录，含目标/范围、最新决定、关键期限、未读材料及未解决复核项；交接状态由已有业务对象管理。M5 增 Server 活跃事项无下一动作巡检，设计可复用但不构成 Personal 排期：没有未完成有效任务、未结期限/庭期或有效等待复查等安排时提醒补安排；已完成历史任务不算有效安排，不自动生成法定期限。
- **复核**：接收资格和事项访问、费用范围分别核查；摘要生成不等于责任已转移，离职/撤权后的读取按当前授权处理。
- **验收**：交接含一个未确认法定期限和一个外部等待；接收人能发现并采取下一步，无权旧成员不能从生成历史读取内容。

### SK11 双语与跨法域一致性核查

- **前置**：原文和译文确切版本、术语表、受众、准据法/程序法域，以及有权使用的对应资料。
- **步骤**：按条款/段落对齐；核对主体、金额、日期、义务、条件、例外与否定；标记遗漏/增译/概念不等价；形成译法建议及需当地专业人员核对的问题。
- **输出**：`BilingualReviewDraft`：对齐表、术语和实质差异、建议表达、法域待核实项。
- **复核**：语言一致不等于法律效果相同；当地适用性须由具备相应能力的人核查，不把翻译功能标成已支持全球法律判断。
- **验收**：包含否定遗漏、金额单位、限定语和不可直接对应的法律概念；应逐项定位，不能静默“统一”为另一法域概念。

以下 SK12 为暂缓参考设计，当前不实现、不安排验收或 M5/M6 恢复日期。它不影响当前 SK07 的人工复核意见、回应和修订记录。

### SK12 复盘、知识提炼与复用

- **前置**：已完成复核的成果、实际反馈、适用范围、材料使用权限和明确选入意愿；原案不因结项自动全所开放。
- **步骤**：提取可复用问题/方法/清单；移除或概化身份及可重识别细节；记录前提和不适用情形；将原案事实与通用方法分开；形成待审核条目；确定受众、版本与复审日期。
- **输出**：`KnowledgeEntryDraft`、方法/模板候选、适用条件、来源受控链接、复审计划及技能改进建议。未来另行恢复后再评估将已审条目组合为有版本的作业包/条款立场，记录首选/可接受/需升级复核的处理、例外及依据，不把旧案结论直接变成通用法律规则。
- **复核**：真实用户检查脱敏、披露范围和方法正确性后发布；普通使用者无需且不得因此获得原案访问权。经验不能充当法律权威。
- **验收**：含独特金额/地点/组合事实的样本需要识别再辨认风险；撤回知识条目后停止新检索；旧引用保留状态提示和权限检查，不重新泄露原案。

## 14. 评测与上线门槛

### 14.1 共同评测维度

| 维度 | 评测方式 |
| --- | --- |
| 可追溯 | 逐条核对来源是否存在、可定位、版本一致、实际支持论断；有链接不等于引用正确 |
| 覆盖与反证 | 与律师标注的关键事实、反证、争点及缺口对照；记录漏项和误报 |
| 专业判断 | 核查法律前提、时点、适用条件和不确定性；评价方案是否回应客户目标 |
| 清楚与实用 | 检查目标受众能否理解决定、风险与下一步；记录真实核查和返工时间 |
| 流程连续 | 产物能否被下一环节直接使用，责任/版本/期限/交付状态是否还原 |
| 权限与变更 | 跨事项、财务边界、撤权、材料撤回、版本变化、中断和重复采纳 |

硬性阻断：越权披露、虚构来源或批准、关键事实以未知冒充确认、正式业务未经确认写入、引用漂移、旧任务覆盖新结果。低质量草稿可退回修改；不能用综合平均分掩盖这些问题。

M0/M1 先冻结样本、质量判定方式和人工工作基线；性能另记观察环境，不设门禁；不得预先宣称固定准确率或效率倍数。小样本只证明相应场景，关键专业项由律师核查，不能完全依赖另一个模型自评。

### 14.2 最小评测集

至少覆盖：材料缺页/失败页、长文截断、新旧版本、同名主体、矛盾日期金额、关键反证、过期法规、法域不明、接口无权/故障、源材料撤回、已启用向量服务的同维度嵌入模型切换、等待与法定期限冲突、旧文书批准、实际交付未发生。使用合成或明确获授权的材料，不把客户原件提交公开仓库。

本次参考研究补充的同组场景：同内容不同送达与重复请求；已拒绝候选重跑及新矛盾来源；末页风险/附件反证未进入模型；未收到答辩与已核查未回应；模板条件改变与预览副作用；复核意见回应/新稿处理和直接来源变更。这些归原 AC02—AC13，不新增一组平行验收编号。M5 的 Word 轮次、问题矩阵和双语样本在对应任务开始时单独细化，不追加入 M4 门槛。

AC14 知识脱敏/发布/撤回及本轮暂缓增量不进入当前最小评测集；恢复对应任务时再登记专项场景，不将编号保留理解为本期必须验证。

每次发布记录技能版本、模型/提示/工具配置、输入与预期、实际差异、人工判定、已知局限。失败样本首先进入对应技能和服务的回归范围，不为了一个提示修改重复执行无关全仓测试。

## 15. 与重构计划的接口

1. **M2**：Server 内置材料、稳定来源、多来源事实与上下文形成可编辑保存的预览；SK01/SK02 的人工流程先完整可用，自动候选按实际模型配置另验。Personal/W17 不是前置，争点要点不冒充完整法律分析。
2. **M3**：W09.1、W10—W12 保留范围接通研究、已有方案/指示、轻量模板、人工复核、轻量同案依赖/等待、人工简报及实际交付；W09.3/B/E/F 深化与 C 通用机制均非门禁。
3. **M4**：Server 实际产物验证核心工作包、团队授权、后台执行、升级与完整恢复；可选服务只对实际启用能力留证，不要求个人产物或外部账号。
4. **M5/M6**：SK10、SK11 及其他专业/法域扩展按真实需要评估；SK12 知识沉淀及本轮暂缓子范围维持最低优先级，不自动重入。

这些技能的主要成本是数据质量、步骤、来源核验、交互和业务校验；现有 TS/Zod/Prisma/队列已经提供可复用入口。本轮没有证据表明需要先把业务改写成 Rust。只有在原型或运行数据指出明确瓶颈时，才按[架构方案](REFACTOR_DESKTOP_TEAM_RAG.md)替换局部组件。
