# 第二轮实验分析：庭审对抗图大师 → LexOrder 诉讼分析工作台

## 结论

这个仓库最值得借鉴的是它的**分析母表作为单一事实来源**，再由母表派生庭审对抗图。LexOrder 应吸收其业务分层和核验纪律，而不是直接复制静态图或五类要点页面。

## 业务结构

1. 诉请固定：请求内容、类型、主体、金额构成与适用边界。
2. 对抗部分：本诉与反诉分别组织，关联请求权基础/法律关系。
3. 要件与争议：完整要件保留在母表；只有「有争议待证」的要件进入对抗图。
4. 四段攻防：请求方主张、抗辩方回应、请求方反制、抗辩方再回应。
5. 法院审查：审理标准、证明责任、证明标准。
6. 证据评价：关键证据、证明前景、决定性、法律置信、证据置信、待补材料。
7. 案件范围：程序站、已获取/未获取材料、材料成熟度、初步研判。

## 关键设计规则

- 一个争议待证的构成要件一个独立行组，不是一个诉请一个争点。
- 默示满足的要件保留在母表，不进入有效争点图。
- 四段攻防正文必须来自当事人或代理文书原文，AI 只提取、分类、定位，不生成对方未说过的主张。
- 证明前景与胜诉概率不同；法律置信与证据置信分开。
- 形成/确认之诉要先识别方法边界，不得机械套用给付请求权的构成要件拆解。
- 本诉/反诉的主体方向要显式建模；反诉不混入普通抗辩四分法。
- 缺少某份文书与已取得文书但无书面记载，法律意义不同。
- 图与表必须共享同一分析数据，并可从图节点回到母表行和固定原件。

## 对 LexOrder 的增量要求

上游 `evidence` 只是自由文本，不够支撑 LexOrder。每个事实、攻防段、法律来源和证据关系都应有独立来源记录，至少固定：
- `Document.id`
- document revision/version
- SHA/hash
- page number
- text-range/paragraph anchor
- source segment type（claim/response/counter/second）
- extraction origin（原文摘录 / OCR 转写 / AI 摘要）
- lawyer review status and reviewer/time

不要用 `SRC_DEFAULT` 替代真实来源；没有 `src` 就显示「来源未关联」，而不是自动显示「起诉状」等默认文书名。

## 发现的上游实现问题

- `build_matrix.py` docstring 说 16 列，`COLS` 实际 17 列。
- `build_matrix.py` 的函数注释说不冻结，但代码实际 freeze B8 并设置筛选；版面约束文档也要求冻结。
- `to_figure.py` docstring 说只取决定性/第一条，代码已改为输出全部争议待证要件。
- `check_claims.py` 未强制四段非空内容必须具备 `src`。
- `to_figure.py` 对缺失 `src` 会回退默认文书名；空段归因参数 `_blank` 计算后未被 `add()` 使用。
- 示例 P1 的形成之诉声明法律关系分析法，却保留构成要件行；P3 反诉未绑定 claims 中的具体请求。
- P1-1 再回应标「无书面记载」，但 scope 标明质证意见未获取。

这些应先回到上游业务模型/样例澄清，再确定 LexOrder 的映射，不应在 UI 中替样例“修正”。
