# LexOrder 案卷材料工作区与接件流程审查（v9）

## 1. 本轮结论

本轮只做隔离 HTML 预览的轻量视觉修整与业务事实校正，不修改 LexOrder 正式源码、数据库、Tauri 壳或导航代码。

保留已经确认的主结构：Chronicle 统一侧栏、案件上下文、左侧材料列表、右侧正文阅读区。进一步收敛为：

- 案件目录是持续展示目录绑定、外盘连接、归档锁定和恢复状态的面板，可以保留右侧 Sheet。
- 材料详情与版本历史使用居中 Dialog；不把普通查看、添加或编辑动作默认放入抽屉。
- 添加材料是明确的接件操作流，使用大尺寸居中 Dialog，底部固定操作区。
- 文字层级整体放大，减少 9–10px 的微小说明、过度标签和解释性长句。业务必要的字段、状态、权限与来源仍然保留。

## 2. 事实矩阵：分类来源

这些名称不是同一维度，不能放在同一组“材料类别”选项里。

| 界面名称 | 事实来源 | 应如何呈现 | 不应如何处理 |
|---|---|---|---|
| 全部材料 | UI 视图，不是数据库枚举 | 快捷视图默认项 | 不新增 `DocumentCategory.ALL` |
| 证据 | `DocumentCategory.EVIDENCE` | 材料类别筛选中的一个选项 | 不与来源、状态混用 |
| 工作稿 | 不是 `DocumentCategory` 枚举；是面向当前可编辑副本的操作视图 | 明确标为“当前可编辑工作稿”，由工作副本身份、状态、格式和版本关系共同决定 | 不新增伪类别；不能仅凭文件名或扩展名认定可编辑 |
| 法院来件 | 独立业务流程入口：全局导航「事务 → 法院来件」 | 作为独立工作区处理来件、去重、案件匹配和附件处置 | 不作为材料类别或快捷材料视图 |
| 法院送达 | `DocumentSourceOrigin.COURT_SERVED` | 材料来源筛选项 | 不能将该字段本身解释为“来件已核验/已处理” |

### Schema 中的真实枚举

**`DocumentCategory`：**

- `EVIDENCE` — 证据
- `PLEADING` — 诉辩文件
- `PROCEDURE` — 程序文件
- `JUDGMENT` — 裁决
- `CONTRACT` — 合同
- `OTHER` — 其他

**`DocumentSourceOrigin`：**

- `CLIENT_PROVIDED` — 当事人提供
- `COURT_SERVED` — 法院送达
- `AI_EXTRACTED` — AI 识别生成
- `SELF_COLLECTED` — 自行调取
- `TEAM_PRODUCED` — 团队产出

**`DocumentStatus`：**

- `DRAFT` — 草稿
- `PENDING_REVIEW` — 待审核
- `APPROVED` — 已批准
- `FILED` — 已入卷

另外，`Document.sourceParty` 是单独字段；现有上传组件仅对 `PLEADING`、`EVIDENCE` 开放来源方选择，并根据所选程序提供可选来源方。`folderId` 是卷宗归属，独立于类别和来源。

### 关于“工作稿”判定的边界

当前隔离预览用一个**演示层派生条件**筛选工作稿：草稿状态、团队产出来源、受支持的 Office/TXT 扩展名、非历史项且当前版本。这个条件不是 Schema 枚举，也不能直接升级为正式领域规则。正式实现必须对照个人版真实工作副本登记、原件/工作副本/回传版本身份以及默认编辑器能力进行判定；扩展名只能作为格式能力提示，不能作为材料身份或权限依据。

### 关于法院来件的边界

正式上传服务分别读取 `category` 和 `sourceOrigin`，校验案件、程序、环节、卷宗归属、权限、文件类型与归档写入限制，再将文件交给 `ingestMaterial`。上传服务接受 `COURT_SERVED` 作为来源值；没有证据表明仅设置该来源值就会自动证明法院来件的去重、案件匹配或建议确认已完成。因此 v9 删除了原先误导性的“法院送达（已核实入卷）”文案，并明确提示：法院来件处理流程与材料来源标记是两回事。

## 3. 添加材料：真实业务操作流

正式网页已有 `MaterialUploadDialog`，不是单纯的文件选择器。预览应保留其关键行为，而不是重新发明一套简化上传。

| 阶段 | 用户操作 | 必须保留的规则 |
|---|---|---|
| 1. 选择文件 | 多选或拖入文件，加入暂存队列 | 选择文件不等于上传；校验格式、空文件、20 MB 限制；显示每个文件 |
| 2. 逐件核对 | 为当前文件确认名称、类别、来源、程序、环节、适用时的来源方 | 每件独立编辑；共同默认值只能应用到仍可编辑、未提交的项目；切换案件/程序/环节后重新验证上下文 |
| 3. 提交与回执 | 逐件提交，查看结果，必要时核对原请求或重试 | 每件独立结果；保留请求键；未知结果不能盲目新建请求；已有上传意图的项目按原请求继续/核对；成功项不重复上传 |

当前正式组件涉及的状态包括 `DRAFT`、`SENDING`、`REJECTED`、`UNKNOWN`、`INCOMPLETE`、`SAVED`、`CLOSED`。界面应清楚区分“校验拒绝”“结果未知”“上传未完成”和“已保存”，不能统一显示成失败。

### 法院来件附件

法院短信、电子送达原文和待处理附件先走独立「事务 → 法院来件」流程，完成去重、案件匹配与附件处置后，再按业务动作归入案件材料。入卷后的材料来源可以记为“法院送达”。来源字段不替代法院来件工作流，也不构成其完成凭证。

## 4. 交互与布局原则

- 主工作区继续使用左侧材料列表、右侧正文阅读区；阅读是主要工作，不将正文塞进抽屉。
- 文件名打开内容；行尾菜单放次要操作；材料详情与版本历史使用 Dialog。
- 案件目录 Sheet 是有理由的例外：它持续显示物理路径、连接状态、归档状态、错误归属拒绝和恢复入口。该信息不适合临时确认弹窗。
- 添加材料、批量归卷、移出确认等任务型动作使用居中 Dialog；不使用侧边抽屉。
- 批量接件 Dialog 有清晰步骤、暂存队列、当前文件详情、固定底部提交区。步骤提示简短，不用大段解释用户正在做什么。
- 类别、来源、状态、卷宗、程序分别呈现；不要把它们合并成一个标签体系。
- 案件切换、筛选、选中材料、版本深链接仍按案独立恢复；同名材料按 Document ID 区分。

## 5. v9 视觉修整

保留 v8 的布局、主题和主要控件，不做大改版。具体修整：

- 正文基础字号从 13px 提到 14px；侧栏导航、表格文件名、表单标签、对话框说明同步放大。
- 减少 9–10px 的次要说明，状态和元数据仍可读但不抢正文层级。
- 缩短添加材料标题下说明和三阶段描述，使用“先选文件，再逐件核对，确认后提交”等直接文案。
- 隐藏面向设计评审的“真实字段与交互参考”按钮；详细出处放在本审查文档和 Issue，而不是混入日常办案界面。
- 取消“法院送达（已核实入卷）”错误暗示。
- 保留 Chronicle 冷灰与钴蓝主题、侧栏和左右分栏比例。

## 8. 建议正式实现验收条件

1. 材料类别筛选仅包含六种 `DocumentCategory`；材料来源筛选仅包含五种 `DocumentSourceOrigin`；状态筛选独立于二者。
2. “全部材料”是默认 UI 视图；“当前可编辑工作稿”是有明确来源、版本、工作副本身份的派生视图；“法院来件”保留独立流程入口。
3. `COURT_SERVED` 不显示“已核实/已处理”字样，除非后端有对应处理记录或状态可证明。
4. 添加材料使用大尺寸居中 Dialog，支持多选/拖入、暂存、逐件核对、共同默认值、逐件提交、结果核对、原请求重试和失败恢复。
5. 已保存项不会重复上传；未知结果不生成第二个请求；错案、程序不匹配、环节不匹配、来源方不适用、归档只读均显示对应拒绝原因。
6. 只有案件目录等持续展示多项本地状态的场景使用 Sheet；材料详情、添加材料和确认操作使用 Dialog 或主阅读区。
7. 文件阅读与版本历史绑定明确 Document ID/version；冻结 V1 不被 V2/V3 覆盖；同名文件不混淆。
8. 通过 Chronicle 的 Base UI/现有封装完成焦点恢复、Escape、背景点击、键盘操作、滚动和 `prefers-reduced-motion` 验收。
9. 用两案合成数据验证切案、重开、同名文件、错案目录拒绝、外盘失联、只读/归档与返回状态；不使用生产数据。
