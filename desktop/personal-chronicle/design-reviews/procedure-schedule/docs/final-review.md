## 2. 最终页面结构

### 2.1 程序管理（程序总览）

左侧 Chronicle 侧栏仍由统一应用壳维护，业务页不创建第二套菜单。

进入案件的「程序」后，正文显示「程序管理」页面。页面列出当前案件全部程序，每行集中展示：

- 程序名称、程序类型、受托／关联性质
- 审理机构和案号
- 当前程序状态
- 实际受理日期和实际终结日期
- 环节、庭期、期限和待办数量
- 「进入办理」操作

右上提供「新建程序」和「全案任务」入口。程序列表按登记顺序呈现，但顺序不表示法律上的前后依赖；程序可以并存。

视觉上使用普通列表行，不使用 KPI 小方块，不重复显示任务完成率、已办结数和已取消数等低优先级指标。

### 2.2 当前程序任务工作区

从程序总览点击某一程序后，进入该程序的独立工作区：

- 正文标题为程序名称，状态和程序类型与对象信息一起展示。
- 主区域显示当前程序的律师准备任务，支持 Board / Table、真实环节筛选。
- Board 只使用业务真实状态：待办、已办结、已取消；不允许拖拽直接改法律办理状态。
- 任务卡片显示任务名称、环节、计划完成时间，以及必要的等待／阻塞原因。卡片不重复展示程序标签、任务 ID 和已由列头表达的状态。
- 右侧展示程序基本信息、庭期和法律期限。庭期、期限是独立对象，不混入 Task。
- 新建任务和任务详情均为完整正文页面，不使用右侧 Sheet。

事项级任务通过「全案任务」入口访问；没有 `stageId` 的任务不会被推断为属于当前程序。

### 2.3 其他入口

- 跨案责任板和 Calendar 继续作为全局日程入口下的内容视图，不增加左侧菜单。
- 责任板、Calendar、案内任务详情按原业务对象 ID 定位同一记录。
- 未转案急务回到原 Intake，不创建虚假 Matter、Procedure 或 Task。
- 材料版本和冻结清单继续使用原材料 ID；冻结 V1 与后继 V2 分开。

## 3. 统一 Chronicle 侧栏边界

本组只维护业务内容区，不自行维护应用壳。

- 左上工作区切换器是唯一切案入口。
- 「当前案件」和「工作区」分组、菜单名称、顺序、二级入口和路由激活由统筹维护。

## 4. 业务对象与真实规则

| 对象 | 真实关系 | 页面规则 |
|---|---|---|
| MatterProcedure | 案件可关联多个程序；程序状态有 `PENDING / IN_PROGRESS / CONCLUDED` | 总览显示全部程序；程序可并存，不用列表顺序推断前置 |
| MatterStage | 环节归属于某个 Procedure | 程序工作区只显示当前程序的真实环节 |
| Task | 归属于 Matter，可选 `stageId`；没有环节时为事项级任务 | 只有真实 `stageId` 才能列入程序工作区；不按日期或同案关系推断 |
| WorkResponsibility | 独立保存责任、状态、修订和处置历史 | 办结、取消、重开保留原因、版本、等待和前置校验 |
| Deadline | 归属于 Procedure，支持 `DATE / DATETIME` | 与任务计划完成时间分开；任务操作不能修改法律期限 |
| Hearing | 归属于 Procedure，记录实际庭期事实 | 单独显示，不当作律师准备任务 |
| Intake | 转案前收案对象 | 未转案事项回到原收案，不创建 Matter 或 Procedure |

### 程序状态与任务状态

- 律师可以在一审办理期间准备二审，但准备任务不能证明二审已被法院受理。
- 任务办结不等于程序终结。
- 程序终结应记录实际日期、结果和审计；案件结案、归档和锁卷仍由案件归档工作区处理。
- 已终结程序的历史任务、庭期、期限应保留。普通新增未来安排应拒绝；历史补录需独立依据、权限和审计，不能复用普通新增动作。
- 任务计划、办结、取消、重开不能改写法律期限。

## 5. 源码审查中发现的服务端缺口

以下为此前对 `main@95eabf3f` 的源码审查结论，正式实现前应重新核对最新 main：

### A. 程序环节新增／恢复缺少父程序终结校验

`materializeProcedureStage` 会锁定程序并检查案件权限，但此前源码未统一检查父程序是否已终结。

建议在同一事务、同一程序锁下校验父程序状态。若要补录历史环节，应设计独立的历史补录动作，要求事实依据和审计。

### B. 庭期新增缺少程序状态守卫

此前 `addHearing` 检查案件权限和可写状态，但没有像个人模式 `addDeadline` 一样复核父程序状态。

应先明确未来庭期与历史庭期补录的边界，再在服务端事务内落实守卫。UI 隐藏按钮不能代替服务端授权和状态校验。

### 已有保护

- 个人模式 `addDeadline` 在写事务中锁定并检查父程序是否开放。
- `createTask` 选择真实环节时检查环节所属程序；事项级任务不伪装成程序任务。
- `updateTask` 改挂其他环节时复核新程序状态。
- `resolvePersonalTask` 重开环节任务时检查所属程序状态。
- Task 处置继续复用责任事务，保留修订、等待、前置和原因校验。

## 6. 视觉规则（本轮第三次精简）

本轮不是通过缩小字号减少信息，而是减少重复信息和装饰性组件：

- 保留自然的大标题（页面标题 25px），不使用英文大写 kicker 或 Hero 区。
- 程序总览采用普通列表行，不为每个指标创建小卡片。
- 程序名称、机构、案号作为主信息；状态和实际日期集中表达。
- 环节、庭期、期限、待办用普通数字和文字呈现。
- 任务卡片删除重复的任务 ID、程序标签、状态标签和头像；状态由 Board 列头表达。
- 正文信息以 14px 及以上为主；任务标题 16px；程序标题 25px。
- 不新增横向模块 Tab，不新增第二套左侧菜单，不把业务关系写成一堆小字说明。
- Chronicle 顶栏、面包屑、搜索、时间和只读切换属于共享壳，本组未擅自修改。

## 8. 正式实现建议

1. 复用 Chronicle 统一侧栏和应用壳，不复制导航。
2. 将程序入口调整为「程序总览 → 当前程序工作区」两层页面。
3. 程序工作区任务列表按真实环节过滤，保留 Board / Table 和三种真实任务状态。
4. 新建程序、新建任务、任务详情采用可刷新正文路由。
5. 右侧信息区仅承载当前程序的程序信息、庭期和法律期限。
6. 复用现有程序状态动作、责任事务、期限和庭期服务；不增加第二套状态引擎。
7. 先确认历史庭期／环节补录规则，再补服务端守卫。
8. 保留原 Procedure、Stage、Task、Deadline、Hearing、Intake ID 和历史深链接。
9. 团队派单、跨人交接和主管接管不进入个人版。
